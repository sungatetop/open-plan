# BRD-002 单主仓库共享核心，双壳演进

- 状态：方向有效（2026-09-20 决策）；**基线数字已过时，实施前须重新测量**
- 出处：`docs/plans/2026-09-20-001-规聚网页端与桌面端协同演进完整计划.md`

## 背景

桌面端立项时面临"平行维护一套桌面业务代码"还是"单主仓库共享核心"的选择。当时（v0.11.2 基线）平台耦合集中在 Express 路由、Agent 运行时与前端通信细节中。

## 决策

1. 以当前仓库为**唯一主仓库**，不平行维护独立桌面业务代码。
2. 网页端与桌面端共享：React 界面、领域服务、Pi Runtime 适配、会话与 Run 数据模型、权限规则、事件协议、工作区与成果管理。
3. 两个端只在平台入口与操作系统能力上分壳：网页端走 HTTP/SSE，桌面端走 IPC/JSON-RPC。
4. 总策略：先稳定基线 → 以服务边界抽取代替大规模目录重写 → 建立同一套能力协议 → 桌面端先可用壳与真实模型闭环。
5. 每阶段同时交付网页端回归、桌面端增量与共享协议测试，不允许"桌面先分叉、以后再合并"。

## 后果

- 正面：一份业务逻辑，两端一致；协议测试成为共享资产。
- 代价：平台桥（协议层）需要显式设计与版本化。

## 现状

- 服务边界抽取尚未开始；本决策的"能力协议"思想已由后续 Tauri 路线（BRD-007）继承——Tauri sidecar 直接复用现有 HTTP/SSE 服务端，即"共享核心"的最小实现。
- 原计划中的 Electron 主进程/IPC 细节已被 BRD-007 取代；本决策保留其"共享核心、不复制业务"的原则。
