# 多用户隔离与桌面端路线梳理

> 结论先行：规聚当前是**单用户本机应用**（单进程、单工作区、单配置目录），要上线部署必须先补三层隔离（用户 → 工作区 → 运行时），桌面端建议走 **Tauri 壳 + 本地优先** 路线，而不是先做 SaaS 多租户。

## 一、现状盘点（哪些是单用户假设）

| 层 | 现状 | 单用户假设点 |
|---|---|---|
| 配置 | `%APPDATA%/规聚`（凭据.json / 模型配置.json） | 全机一份，无用户维度 |
| 工作区 | `office-workspace` 单目录，前端可切换本地项目 | 会话/产物/记忆都落在同一工作区 |
| 会话 | JSONL 存 `.规聚会话/` + `.oaw/runs/` | 按 threadId 组织，无 owner 字段 |
| 服务 | Express 单端口，无鉴权 | `/api/*` 默认同源可访问 |
| Agent | Pi 运行时全局单例 + 并发调度（agent limit 2） | 凭据全用户共享 |
| 地图/知识库 | `maps/`、`kb.mjs` 索引挂在工作区下 | 跟随工作区，天然可隔离 |

## 二、三层隔离方案

### 第 1 层：用户隔离（认证与配额）
1. **认证**：加最小鉴权层——登录（用户名密码或 OAuth），签发 HttpOnly Cookie/JWT；Express 加 `requireAuth` 中间件，全部 `/api/*` 强制过闸。SSE 也要带凭证（EventSource 不带 header，用 Cookie）。
2. **用户身份贯通**：引入 `userId`，写进 TaskEnvelope / Run manifest / 会话 JSONL 的元数据（不加字段就无法事后审计）。
3. **配额与限流**：每用户并发 Run 数、token 用量月度配额（复用现有 scheduler 的 limit 结构，从全局 limit 改成 `perUser × 全局上限` 双层）。
4. **凭据归属**：`凭据.json` 拆成 `凭据/<userId>.json`；模型套餐（如 OpenCode Zen Go）支持"平台共享 Key"与"用户自带 Key"两种模式，配额分别记账。

### 第 2 层：工作区隔离
1. **目录模型**：`workspaces/<userId>/<workspaceName>/`——office 文档、maps/、kb 索引、.规聚会话、.oaw/runs 全部跟随工作区目录（现有 `workspace` 参数已贯穿大半 API，改造面可控）。
2. **路径安全**：所有文件 API 已有 `isInside(ws, fp)` 校验，多用户下必须再钉死两条：符号链接逃逸、`..` 归一化后二次校验；officecli/map_edit 的写路径同样过闸。
3. **共享与协作（后期）**：先做"只读共享链接"，再做多人文档（需要 CRDT 或锁）；知识库图谱跨工作区引用要显式声明，不默认互通。
4. **备份与配额**：每工作区磁盘配额；runs/ 产物快照的保留策略按套餐分级。

### 第 3 层：运行时与计算隔离
1. **Pi Runtime 池化**：当前嵌入式单例要改成 per-user（或 per-session）Runtime 实例池；模型请求走各用户自己的凭据与网络设置。
2. **进程边界**：officecli、bash 类工具在服务端跑，多用户下必须放沙箱（Windows 下 Job Object + 临时目录 jail；Linux 容器/nsjail）。**没有沙箱前不要公网开放 bash 工具**。
3. **队列公平性**：scheduler 从 FIFO 改为按用户轮询，防止一个用户的长任务饿死他人。

## 三、部署形态分三步走

| 阶段 | 形态 | 关键工作 | 适合场景 |
|---|---|---|---|
| ① 内网/团队版 | 单服务器 + 反向代理 + 多用户鉴权 | 第 1+2 层 | 5-50 人团队自部署 |
| ② 云 SaaS | 容器化（每用户一个轻量 Runtime 容器）+ 对象存储 + 计费 | 第 3 层 + 运维 | 公网多租户 |
| ③ 混合 | SaaS 控制面 + 用户本地算力（模型 Key 在用户侧） | 凭据不出本地的架构确认 | 企业合规场景 |

## 四、桌面端路线（大问题的解法）

**推荐：Tauri 壳 + 本地优先**（与 AGENT.MD 调研结论一致，但补充部署协同）：

1. **打包**：Tauri 2 壳复用现有 React 前端 + Node 服务端（sidecar 进程跑 `server/index.mjs`，或用 bun compile 成单二进制）。officecli 作为外部依赖随安装器分发。
2. **本地优先的好处**：文档/凭据不出用户机器（合规叙事强）、无服务器成本、天然规避多租户隔离的大部分难题——**桌面端本身就是最强的隔离**。
3. **与云端的关系**：桌面端做成"节点"，SaaS 做控制面（账号、套餐、同步、协作信令），工作区数据默认本地、用户显式开启同步。这样桌面与 SaaS 共用一套代码：`FEATURE_CLOUD` 开关 + 服务端鉴权层按环境装配。
4. **更新**：Tauri updater + 增量更新；officecli 等外部二进制单独自更新（它们版本节奏与主程序不同）。
5. **顺序建议**：先做 ①内网版（验证多用户与鉴权），同时起 Tauri 壳（成本一两周量级）；SaaS 多租户放最后——它依赖前两者的全部沉淀。

## 五、落地顺序清单（按依赖排序）

1. `requireAuth` + userId 贯穿（会话/Run/产物元数据）
2. 凭据按用户拆分 + 套餐配额记账
3. 工作区目录模型改造 + 路径安全加固（含 officecli/map_edit）
4. Pi Runtime 池化 + scheduler 公平调度
5. 工具沙箱（bash/命令类工具白名单化）
6. Tauri 壳 POC（sidecar + updater）
7. SaaS 化（容器编排、对象存储、计费）
