# Qoder 能力逆向引入方案

> **依据：** `Qoder逆向技术调研报告.html`（逐模块逆向取证，标注 `observed`/`inferred` 与字符偏移）。本方案对该报告的**能力清单做逐项可引入性判定**，并为可引入项给出逆向改造实施方案。
> **关系：** 与 `2026-10-18-001-Qoder对标整改与交通规划Harness迭代修改计划.md`（下称"计划 001"）为**增量关系**——计划 001 覆盖对标报告 §2/§3/§4 的 18 项偏差；本方案从**逆向报告本身**重新过一遍全部能力，捞出计划 001 未覆盖、但对规聚确有价值的项（编号续排 `P1-9…`、`P2-7…`）。
> **范围声明：** 计划 001 §9 曾声明"不引入报告之外的新目标"。本方案是**用户明确要求的范围扩展**，因此：① 本文档新增项全部来自逆向报告的**实际取证能力**（非新造）；② 新增项仍受"不改 Pi 内核、不新增产品形态、不做皮肤引擎"三条边界约束；③ 计划 001 的范围声明需随本文档一并更新（见 §9）。

## 〇、判定口径

### 0.1 判定档位

| 档位 | 含义 | 处置 |
|---|---|---|
| **可直接引入** | 与规聚既有架构同构，按现有落点接线即可 | 进 §2 实施方案，排入阶段 |
| **需改造引入** | 语义等价但形态不同，需做映射/适配层 | 进 §3 实施方案，排入阶段 |
| **暂缓** | 收益成立但依赖前提未满足（如进程模型变更） | 进 §4，触发条件成立再启动 |
| **不引入** | 越界（改内核/新形态）或过度设计（成本 > 收益） | 进 §5，写明理由供后续复核 |

### 0.2 判定维度

1. **是否在 open plan 预设范围内**（`REQUIREMENTS.md` R1–R9 + 非功能需求）
2. **是否触碰 Pi 能力边界**（`AGENT.MD`：不改内核、不引入官方不存在的 subagent/plan mode）
3. **是否与既有模块冲突**（130+ 事件注册表、运行预算、子代理契约、成果验收）
4. **收益/成本比**（专业工具场景下是否值得）

### M1 新增项（2 项）

#### `P1-17` 空闲超时按"每块重置"语义

- **逆向要点：** Qoder 两套 SSE 都用**空闲超时**而非固定读超时——Cloud SSE「60s 空闲，每收到数据块即重置计时器」；Remote Control 是「90s 读超时，每成功读到数据即重置」。差异点在于**计时基准是"数据到达"而非"连接时长"**。
- **规聚现状：** 对话流心跳 5s（服务端定时发）、客户端静默 20s 强制重连、握手 50s 兜底——三个**固定阈值**，长任务中若 Agent 长时间无输出（正常现象，如 officecli 生成大文档），20s 看门狗会误判重连。
- **改造方式：**
  1. 服务端把定时心跳拆为两种：**周期心跳**（保活，保留 5s）+ **空闲探测**（距上次**业务事件**写出的时长）。
  2. 客户端看门狗基准由"距上次任意信号"改为"距上次**业务事件**"，心跳不计入业务事件，避免心跳掩盖真实静默。
  3. 静默阈值可配（与 `P2-2` 心跳可配合并到同一环境变量族）。
- **落点：** `server/index.mjs`（对话流写出口）、`server/流连接.mjs`（空闲计时）、`client/src/components/ChatPanel.jsx`（看门狗基准）。
- **依赖：** 无。
- **验收：** `test:sse-protocol`、`test:chat-flow` 全绿；新增断言——模拟"心跳持续但业务事件静默 60s"，断言**不触发**重连；模拟"心跳与业务事件同时静默 25s"，断言**触发**重连。

#### `P1-19` `input-not-delivered` 输入未投递回执

- **逆向要点：** Qoder L2 事件字典含 `input-not-delivered{inputId}`——**流异常终止导致输入未投递时显式回执**，前端据此提示重发。这是"发了没反应"类体验问题的结构性解法。
- **规聚现状：** 提交走独立 POST，若流在发送窗口异常终止，前端无判别依据（用户只能看到"没有回复"）。
- **改造方式：**
  1. 服务端在接受输入时登记 `inputId`（复用 TaskEnvelope 的既有 id），在 SSE 建流/写入失败路径派发 `input_not_delivered`（**需登记事件**，`lifecycle:true`）。
  2. 前端收到后：把该条用户消息标记为「未投递」，内联提供「重新发送」按钮（复用既有重发路径）。
- **落点：** `server/index.mjs`（POST 发送路径 + 流失败路径）、`server/事件注册表.mjs`、`ChatPanel.jsx`。
- **依赖：** `P1-3`（先订阅后发送为强前提，否则无法判断"未投递"）。
- **验收：** 新增 `scripts/输入未投递回执测试.mjs`——构造建流失败/写失败两例，断言事件派发 + 前端出现「未投递 + 重发」。

### M2 新增项（9 项）

#### `P1-9` 显式投递模式（steer / queue）+ 续接绑定　★重点

- **逆向要点：** Qoder 把"用户在与 Agent 交互中追加输入"抽象为 `deliveryMode: "steer" | "queue"`：`steer` 走 `steerContinuationTurnId` 续接到当前轮次（不新开轮次），`queue` 进等待队列。配套 `observeContinuation(messageId)` / `bindContinuation(afterMessageId, turnId)` 把续接消息**显式绑定**到轮次，避免"幽灵轮次"。
- **规聚现状：** `AGENT.MD` 已知坑明确记录了同一问题——「并发 prompt：agent 收尾（compaction/post-run）时 `entry.busy` 已 false 但 pi 内部仍 `isStreaming`，直接 prompt 会抛 `Agent is already processing` → **已加竞态重试（走 steer）**」。也就是说规聚**已经在走 steer，但它是隐式的、错误驱动的一次重试**，没有语义化的模式选择与绑定关系。
- **改造方式：**
  1. 把隐式重试上升为**显式投递契约**：`ExecutionInput` 增 `deliveryMode`；默认 `queue`（安全），Agent 运行中用户插话时前端可显式选 `steer`。
  2. 实现 `observeContinuation` / `bindContinuation` 等价物：续接消息记录 `afterMessageId` 与目标 `turnId`，归约层据此把消息渲染在**正确的轮次内**（而非追加为新轮次）。
  3. 前端输入区在 Agent 运行中显示「插话（转向）/ 排队」二选一；选「转向」时消息标注归属轮次。
  4. 保留原竞态重试作为**兜底**（A/B 双保险，`AGENT.MD` 既有做法不动）。
- **落点：** `server/执行句柄.mjs`（`deliveryMode` 分支）、`server/agent.mjs`（steer 落点显式化）、`client/src/运行展示投影.js`（续接归属）、`ChatPanel.jsx`（输入区模式选择）。
- **依赖：** `P1-1`（执行句柄为强依赖）。
- **验收：** 新增 `scripts/投递模式测试.mjs`——① `steer` 时消息归属当前轮次、不新开轮次；② `queue` 时进队列并在前序结束后执行；③ 竞态场景下隐式重试兜底仍生效（原有断言不回归）。
- **风险：** 显式 `steer` 若被滥用可能造成轮次过长。缓解：`steer` 单轮上限次数（如 5 次）后自动降级为 `queue`。

#### `P1-10` 执行拒绝码族 + `availability` 三态 + 并发漂移检测

- **逆向要点：** ① `execute()` 返回 `{status, code?}`，8 个标准拒绝码把"为什么不能执行"枚举化（已释放 / 轮次活跃 / 轮次陈旧 / 不支持 / 无活跃轮次 / 发送失败 / 控件准备漂移 / 技能不支持）；② `availability()` 返回 `{state: ready|busy|disconnected, code?}`；③ `ensureCurrent()` 在 prepare 前后**多次复查**，检测并发漂移。
- **规聚现状：** 只有 `SESSION_BUSY` 一个语义（含占用详情），其余"为什么不能执行"靠错误文本。
- **改造方式：**
  1. 定义规聚侧拒绝码族（保留 `SESSION_BUSY`，新增 `RUN_TURN_ACTIVE` / `RUN_TURN_STALE` / `RUN_HANDLE_RELEASED` / `RUN_CONTROL_UNSUPPORTED` / `RUN_TURN_NOT_ACTIVE` / `RUN_SEND_FAILED` / `RUN_CONTROL_PREPARATION_DRIFT` / `RUN_SKILLS_UNSUPPORTED`），统一从 `执行句柄.mjs` 返回。
  2. `可用性()` 三态驱动前端顶部状态点（与 `P1-16` 的 `waiting-user` 联合使用）。
  3. 引入 `ensureCurrent` 式漂移检测：在 Run 的 admit 与 prepare 两个时点复查三元组（`released / runId / turnId`）。
- **落点：** `server/执行句柄.mjs`、`client/src/components/ChatPanel.jsx`（状态点 + 拒绝码文案映射）。
- **依赖：** `P1-1`、`P0-3`。
- **验收：** 新增 `scripts/执行拒绝码测试.mjs`——8 个码逐一构造触发条件，断言码值 + 前端文案；漂移检测用例断言在 prepare 期间状态变化时拒绝并给出 `RUN_CONTROL_PREPARATION_DRIFT`。

#### `P1-11` 运行时能力协商失败标准码族

- **逆向要点：** `capabilities` 探测（`selected_skills_v1`、`historyRewind` 等）+ `capabilities-changed` 事件 + 明确 UNSUPPORTED 拒绝（`QODER_EXECUTION_SELECTED_SKILLS_UNSUPPORTED`）——**端/云差异显式化而非静默降级**。
- **规聚现状：** 有 `capability_plan` 事件 + 能力契约测试 + `skills/preflight`，但运行时协商失败无标准码，降级路径不统一。
- **改造方式：** ① 定义 `CAPABILITY_UNSUPPORTED` 码族（`skills` / `vision` / `map_tools` / `office_*`）；② 协商失败时派发 `capability_changed`（**需登记**）并返回标准码；③ 前端据此禁用不可用入口并给出原因，**禁止静默降级**。
- **落点：** `server/执行句柄.mjs`、`server/事件注册表.mjs`、`client/src/components/SettingsPanel.jsx`（能力可见性）。
- **依赖：** `P1-1`。
- **验收：** `test:capability-contract` 全绿；新增断言——构造能力缺失，断言返回标准码 + 派发 `capability_changed` + 前端入口禁用。

#### `P1-12` 工作目录级互斥 + `queueReason` 三枚举

- **逆向要点：** 调度互斥粒度是**工作目录（cwd）**而非会话；排队原因枚举 `work-directory-busy` / `-unavailable` / `runtime-unavailable`，直接驱动前端文案。
- **规聚现状：** `agent_queued` / `agent_queue_update` 事件已有，但互斥粒度是会话（`SESSION_BUSY`），排队原因未枚举。
- **改造方式：**
  1. 在既有工作区机制（`server/工作区隔离.mjs` / 工作区切换）之上加 **cwd 级执行锁**：同一工作区已有活跃 Run 时，新 Run 进等待队列（**不失败**）。
  2. `agent_queue_update` 载荷增 `reason` 枚举（`work_dir_busy` / `work_dir_unavailable` / `runtime_unavailable`）。
  3. 前端队列条按原因渲染文案（复用 `P1-16` 状态点）。
- **落点：** `server/执行句柄.mjs`、`server/index.mjs`、`client/src/components/ChatPanel.jsx`。
- **依赖：** `P1-1`、`P1-10`。
- **验收：** 新增 `scripts/工作目录互斥测试.mjs`——同工作区两次并发执行断言第二次排队且 `reason=work_dir_busy`；不同工作区断言**不**互斥。

#### `P1-13` 游标提交规则 + `route-cursor-confirmed` 回执

- **逆向要点：** `confirmCursor` **忽略无稳定 id 的帧**（`event_start` / `event_delta`），只对具备稳定 id 的帧记录 `providerLastEventId`，并派发 `route-cursor-confirmed` 回执。
- **规聚现状：** `id: seq` + query `after` + header `last-event-id` 取最大 + `truncated` 标记，但**未区分"哪些帧可提交游标"**——若把瞬时增量帧的 seq 当作续传点，重连后可能从错误的点续接（漏一帧或重放一段）。
- **改造方式：**
  1. 在事件注册表为每条事件标注**是否可作游标点**（复用既有 `persist` 标记即可：仅 `persist:true` 的持久化事件可作游标点；`token`/`thinking`/`tool_output` 等增量帧不可）。
  2. 客户端游标只取"可作游标点"的最大 seq 提交（`resolveReplayCursor` 内实现）。
  3. 提交后派发 `route_cursor_confirmed`（**需登记**）用于诊断。
- **落点：** `client/src/components/ChatPanel.jsx`（游标解析）、`server/事件注册表.mjs`（游标点标记，若需新字段）、`server/事件存储.mjs`。
- **依赖：** 无（可独立完成）。
- **验收：** `test:sse-protocol` 全绿；新增断言——在仅收到增量帧时**不推进**游标；收到持久化帧后推进；重连后事件序列无缺口无重复。

#### `P1-14` 中断/释放统一收束挂起交互（防 Promise 悬挂）

- **逆向要点：** ① AbortSignal 触发时自动 resolve `{behavior:"deny", message:"操作请求已取消。"}` 并派发 `interaction-cancelled`；② 会话释放时统一以 `deny` 收束**所有**挂起交互——**保证不会有 Promise 悬挂泄漏**。
- **规聚现状：** `ask_user` 已有 5 分钟超时（工作区已实现），`tool_approval_request` 的**取消/释放路径未显式收束**——极端情况下等待中的审批 Promise 可能悬挂。
- **改造方式：**
  1. 在 `审批策略.mjs` / `执行句柄.mjs` 维护 `待决交互表`；Run 被取消或会话释放时，遍历该表统一 resolve 为 `deny` 并派发 `interaction_cancelled`（**需登记**）。
  2. `ask_user` 的超时路径与释放路径统一走同一收束函数（去掉两套逻辑）。
- **落点：** `server/审批策略.mjs`、`server/agent.mjs`、`server/事件注册表.mjs`。
- **依赖：** `P1-4`（owner 归属为表结构前提）。
- **验收：** `test:approval` 全绿；新增断言——构造"审批等待中取消 Run"与"审批等待中切换/关闭会话"两例，断言交互被 resolve、事件派发、无悬挂计时器。

#### `P2-7` 非关键通道失败静默窗口

- **逆向要点：** `recordFailure("background")` → `backgroundPausedUntil = now + 5000`，后台通道失败后**主动静默 5s**，不与主通道抢带宽。
- **改造方式：** 客户端长连接预算（`长连接预算.js`）为低优先级通道（如记忆流、浏览器帧流）增加"失败后静默窗口"；对话流与事件流不受影响。
- **落点：** `client/src/长连接预算.js`。
- **依赖：** `P0-1`（共用失败记录）。
- **验收：** `test:stream-budget` 全绿；新增断言——低优先级通道连续失败后 5s 内不重试，且对话流重试不受抑制。

#### `P2-8` 控制面 401 自动刷新凭据重试一次

- **逆向要点：** Cloud SSE 的 `response()` 做**两次尝试**：`initial` → 401 时用 `unauthorized`（刷新后）token 重试；仅重试一次。
- **改造方式：** `client/src/api.js` 的 `apiControl` 在 401 时触发一次凭据刷新（Pi 配置独立化已有凭据读取路径）并**仅重试一次**，第二次失败即抛出。
- **落点：** `client/src/api.js`、`server/index.mjs`（凭据刷新端点若无则复用既有）。
- **依赖：** 无。
- **验收：** 新增断言——401 → 刷新 → 重试成功；401 → 刷新 → 仍 401 → 立即失败（不循环）。

#### `P2-9` 强制 https（仅 localhost 允许 http）

- **逆向要点：** 传输安全策略：**强制 https，仅 `localhost` / `127.0.0.1` / `[::1]` 允许 http**。
- **改造方式：** `server/index.mjs` 启动时校验对外基址；非本地且非 https 时**拒绝启动并打印原因**（可经环境变量显式豁免用于内网集成测试）。
- **落点：** `server/index.mjs`。
- **依赖：** 无。
- **验收：** 新增断言——非本地 http 基址断言拒绝启动；localhost http 通过；`OAW_ALLOW_INSECURE_HTTP=1` 时豁免。

#### `P1-18` 内容分片归一化（`part-delta`）+ 逐字流式适配

- **逆向要点：** 内部统一模型用 `content{ turnId, part:{kind:"part-start"|"part-delta", index, delta:"text", value} }` 表达内容分片，另有 `part-delta → content_block_delta / text_delta` 的 Anthropic 风格适配用于逐字渲染。
- **规聚现状：** `client/src/components/流式文本队列.js` 已实现流式文本队列；`运行展示投影.js` 做事件归约。缺少"内容分片"与"消息整体"的显式分层。
- **改造方式：** 在归约层引入 `content / part` 概念：`token` 归约为 `part-delta`，`message_start/end` 归约为消息边界；流式渲染消费 `part-delta`。**不改变既有事件名**（避免破坏 130+ 注册表），只在**归约输出**层引入分层。
- **落点：** `client/src/运行展示投影.js`、`client/src/事件展示.js`、`client/src/components/流式文本队列.js`。
- **依赖：** `P1-2`（schema 校验定义内容块形态）。
- **验收：** `test:run-view`、`test:chat-flow` 全绿；新增断言——分片序列可正确重组为完整消息，且重组结果与既有渲染一致。

#### `P2-11` 保留字段规范 + 事件字典补缺

- **逆向要点：** SDK 显式禁止业务消息占用 `session_epoch` / `sequence`（"reserved for daemon-internal Session ordering"）。
- **改造方式：** 在 `事件注册表.mjs` 增加**保留字段清单**（如 `seq` / `streamId` / `clientId` / `threadId` / `ts`），并在注册表测试中断言业务事件载荷**不得**包含保留字段；同时补齐 `P1-13` / `P1-19` / `P2-16` 引入的新事件。
- **落点：** `server/事件注册表.mjs`、`scripts/事件注册表测试.mjs`。
- **依赖：** `P1-2`。
- **验收：** `test:event-registry`、`test:pi-iteration` 全绿；新增断言——含保留字段的事件被拒绝登记。

### M3 新增项（3 项）

#### `P1-15` 业务工作流状态机与执行态解耦　★重点

- **逆向要点：** 业务工作流状态 `backlog / todo / in_progress / in_review / done / cancelled`（次要族 `blocked / archived / deleted`）用 JSON Schema 正则强校验；并有一条**关键设计声明**：「**状态不自动触发 Agent 执行；执行结束不自动代表验收通过**」——业务状态与执行生命周期**显式解耦**，人工验收是独立环节。
- **规聚现状：** 有任务中心 + PlanBoard + 成果管理，但**执行态与业务态混在一起**；`run_finished` 之后直接呈现"完成"，缺独立的"待验收"环节与显式解耦声明。
- **改造方式：**
  1. 在任务/成果模型上引入**独立于 Run 的 `workflowStatus`**，取值对齐 Qoder 六态（中文文案：待规划 / 待开始 / 进行中 / 待验收 / 已完成 / 已取消，次要族：阻塞 / 归档 / 删除）。
  2. 状态机做**合法迁移校验**（如 `backlog→in_review` 非法），非法迁移拒绝并给出原因。
  3. **落地解耦声明**：① Run 结束只把业务态推进到 `in_review`，**不自动置 `done`**；② `done` 必须由人工验收动作触发；③ 前端明确区分「执行态徽标」与「业务态徽标」。
  4. 与计划 001 的 `M5.1 成果验收台` 天然对接：验收台的「采纳」动作即 `in_review → done` 的触发器。
- **落点：** 任务/成果数据模型（`server/成果管理.mjs` 及任务相关模块）、`client/src/components/任务中心.jsx`、`成果验收台.jsx`。
- **依赖：** 计划 001 `M5.1`（成果验收台为 `done` 的触发器）。
- **验收：** 新增 `scripts/业务状态机测试.mjs`——① 六态合法迁移表逐条断言；② 非法迁移被拒；③ Run 结束断言业务态为 `in_review` **而非** `done`；④ 验收台采纳后断言置 `done`。
- **风险：** 引入独立业务态可能与既有任务中心显示冲突。缓解：先做**只读映射**（既有态 → 新态）上线，再切换为可写（两阶段）。

#### `P1-16` `waiting-user` 一等执行态 + 子代理 `paused` 态

- **逆向要点：** 执行态五项含 `waiting-user`（等待回应）——**一等状态**，不是"运行中"的子情形；子代理态含 `paused`（已暂停）。
- **规聚现状：** 对标报告 §1.4 已判定"缺 `waiting-user` 一等状态与'已暂停'态，HITL 等待期间视觉反馈不足"。
- **改造方式：** ① 执行态枚举增 `waiting_user`，在 HITL 挂起时**自动进入**该态，并让顶部状态点变琥珀（与 `§3.3 ①` 状态点色板一致）；② 子代理态增 `paused`（可暂停/恢复子代理），前端子代理卡片增加暂停/恢复入口。
- **落点：** `server/子代理编排器.mjs`（paused 态）、`client/src/components/ChatPanel.jsx` + `子代理详情面板.jsx`。
- **依赖：** `P1-4`（owner）、`P1-10`（可用性三态）。
- **验收：** `test:subagent-orchestrator`、`test:subagent-trace`、`test:approval` 全绿；新增断言——HITL 挂起时执行态为 `waiting_user`；子代理暂停/恢复状态流转正确。

#### `P2-13` 消息级动作（有帮助/没帮助/从消息建任务/复制）

- **逆向要点：** `HOST_ACTIONS`：`copy_text` / `helpful` / `not_helpful` / `create_branch_task` / `copy_markdown` / `add_reply_to_task`。
- **规聚现状：** 有 fork（分支）；缺「有帮助/没帮助」反馈与「从消息建任务」。
- **改造方式：** 消息悬浮工具条增四个动作——复制文本、复制 Markdown、**从消息建任务**（写入任务中心，触发 `P1-15` 的 `backlog`）、有帮助/没帮助（写本地遥测，供 `P2-5` 事件量级遥测聚合）。
- **落点：** `client/src/components/ChatPanel.jsx`（消息工具条）。
- **依赖：** `P1-15`（建任务需要业务状态机）。
- **验收：** 新增断言——四个动作可用；「从消息建任务」后任务中心出现 `backlog` 条目且内容与原消息一致。

#### `P2-17` 模糊分层 + 抽屉 `slide/reveal` 进场

- **逆向要点：** 用模糊量表达层级——遮罩 `blur(2px)`、底影 `blur(24px)`、扫光 `blur(10px)`、base `blur(0.18px)`；`data-drawer-motion = slide | reveal` + `@starting-style` 实现进场。
- **改造方式：** ① 令牌化四级模糊（`--blur-1..4`）；② 抽屉/弹层支持两种进场模式（`slide` 从右侧滑入、`reveal` 原地渐显+微缩放），默认 `slide`；③ 全部纳入 `data-visual-effects=off` 降级范围（与 `P2-4` 同源）。
- **落点：** `client/src/styles.css`、`client/src/components/*`（弹层组件）。
- **依赖：** `P0-4`、`P2-4`。
- **验收：** `test:motion`、`test:a11y` 全绿；新增断言——四级模糊令牌存在；两种进场模式均可用；`data-visual-effects=off` 时模糊归零。

#### `P2-10` 快照/落盘去重（fingerprint）+ 上传背压

- **逆向要点：** workspace 快照循环用**背压从 100 翻倍至 30000** + **fingerprint 去重**，避免重复上传。
- **规聚现状：** `snapshotWorkspace` 存在；去重依赖路径 + mtime + size（KB 索引层），**工作区快照层无 fingerprint**。
- **改造方式：** ① 工作区快照计算内容 fingerprint（路径 + 大小 + 内容哈希短码），未变化则跳过；② 大批量文件时采用递增背压（起始 100ms，失败翻倍至 30000ms）。
- **落点：** `server/index.mjs`（`/api/runs` 与快照路径）、`server/成果管理.mjs`。
- **依赖：** 无。
- **验收：** `test:artifacts`、`test:file-diff` 全绿；新增断言——重复快照被 fingerprint 跳过；大批量场景耗时不劣化。
