# 自研 Harness 全维度对标分析与优化落地计划

- 日期：2026-10-15
- 基线：`open-plan@0.11.52`（`@earendil-works/pi-coding-agent@1.1.0`）+ 上一轮 PI 迭代（子代理编排、编辑流水线、运行预算接线、原生文档引擎）
- 对标对象：**DeepSeek Harness (DSH) v0.2 RC**、**Claude Code**、**OpenAI Codex CLI (Apache 2.0)**、**Google Antigravity CLI (原 Gemini CLI)**、**OpenHands**、**OpenCode**、**Aider**
- 对标基准：[《技术架构分析与内核迁移可行性报告》](./2026-10-14-技术架构分析与内核迁移可行性报告.md) + 实时公开资料（2026-10-15 快照）
- 性质：静态代码审计 + 公开架构对照，**未改动业务代码**

## 0. 结论摘要（TL;DR）

1. **本项目自研 Harness 的"业务厚度"是最大护城河**：Office 场景全链路（原生 docx/xlsx/pptx + 编排器 + 流水线 + 验收）、三栏工作台、知识库、地图/GIS、审批与写锁、供应商导入管线——这些在 2026 年 10 月的主流开源 harness（DSH / Codex CLI / OpenCode / OpenHands / Aider）里**没有一个是开箱具备的**。Claude Code 也没有 GIS/Office/Knowledge Base 这类领域能力，且是闭源黑盒。

2. **自研 Harness 的"内核底座"与业界标准有系统性差距**：沙箱/进程隔离、原生 fork/resume/replay、持久 Job/重启恢复、内核级工具把关流水线、追加式会话日志单事实源——这些恰恰是 DSH 凭借 Cordis 插件架构在 8 月开源后迅速追平的能力，也是本项目 "报告 §4 S1–S10 短板" 的核心。

3. **差距不等于缺陷，而是"定位不同"**：本项目面向 **"领域专家工作台"**（为 Office/研究/GIS 场景做 Agent），DSH/Codex 面向 **"通用代码 Agent 底座"**，Claude Code 面向 **"闭源高质量 Agent 套件"**。三者的能力面是**互补而非替代**。

4. **最佳路径依然是报告结论：不要替换内核，要先"收敛 Harness 短板 → 建立内核 seam → 引入 DSH 作为可选第二个内核"**。上一轮 PI 迭代已经补齐了 S7（子代理弱）、S8（预算治理未完成）的大半，证明"用自研补短板"比"换内核"成本更低。

5. **优化优先级建议**：
   - **最高优先**（不改架构即可闭环）：S1 事实来源唯一、S3 工具硬门禁、S4 持久 Job/重启恢复、S9 事件持久化/幂等
   - **中优先**（借鉴 DSH 设计）：S2 沙箱/进程隔离（Sidecar 方案）、S5 近似 fork/replay
   - **架构级**（需 seam）：S10 内核抽象、S6 token 级 checkpoint（受 Pi 限制，需 DSH 才能根治）

6. **最新情报更新**（对报告 §2 的补充）：DSH 已发布 v0.2 RC（2026-09-29），含 macOS/Windows 桌面端安装包、**实验性 Claude Code Mods 兼容层**（2026-10-03 v0.2.1-alpha.1）、**官方插件市场**规划；GitHub Stars 达 **24.3 万**（截至 2026-10）；官方宣称 ~60% Harness 用户在跑第三方插件。这意味着 DSH 的**插件生态与稳定性预期**比报告初稿时更强。

### 1.5 适用边界

**擅长**：
- 中文办公文档生成/审校（Word/PPT/Excel）
- 本地化研究/咨询工作台（知识库 + 联网搜索 + GIS）
- 多供应商模型接入（33 供应商 / 1142 模型导入管线）
- 长链路领域任务（编辑流水线 + 子代理编排 + 成果验收）

**不擅长**：
- 强沙箱隔离的代码 Agent 场景（Pi 非 Sandbox，bash 直接在宿主执行）
- 需要 fork/branch 会话的协作式开发（nativeFork=reserved）
- 重启后可恢复的长时后台任务（无持久 Job）
- 100% 无外部依赖的 PPT 高级能力（图表/Morph 等仍需 officecli）

#### 与业界标准的差距判断

- **架构哲学**：业界在 2026 年已收敛到 "Everything is Plugin"（Cordis）/ "Agent = Model + Harness"（Böckeler 2026）/ "Harness Engineering"（Ariful Islam 2026）三大范式。本项目尚未采纳，**这是最大的"差距"——不是功能缺失，而是架构选择**。
- **安全模型**：业界已从"应用层审批"收敛到"内核级沙箱 + 工具预执行拦截"。本项目仍以"提示词 + 白名单 + 应用层审批"为主，**在防御纵深上有系统性差距**。
- **可恢复性**：业界已从"同步 HTTP 内执行"收敛到"持久 Job + 追加式日志 + 原生 fork/resume"。本项目的"recovering + 提示词恢复"在正确性和用户体验上均有明显差距。
- **扩展性**：DSH v0.2 + OpenCode 的成功证明"插件生态 + 开放 harness"是 2026 年的主导方向。本项目**硬编码的能力面**（Office/GIS/KB 是优势，但不可插拔）在长期会限制演进。
- **性能**：本项目在 Office 生成场景的首字延迟/产物速度上**反而优于 DSH**（无 Cordis 插件启动开销），这是领域化的优势。

| O10 | 插件化业务能力（MCP 桥接）| Harness | — | 中 | 高 | 中 |

### 3.2 逐项优化方案

#### O1 事实来源唯一化

**技术路径**：
1. 新增 `server/Run事件日志.mjs`：追加式事件日志（JSONL），每条事件唯一 `seq`，支持 `fork(fromSeq)`/`snapshot()`/`deriveMessages()`。
2. `agent.mjs` 的 `emit()` 双写：现有的 `emitChannel`（SSE）+ `Run事件日志`（持久）。
3. 前端 `运行展示投影.js` 改为消费 `deriveMessages()` 投影，而非直接消费 Pi 事件。
4. 历史 Run 回放全部从日志重建。

**预期收益**：S1 根治；为 O5 fork、O3 重启恢复、O9 DSH 接入奠定基础。

**资源投入**：~3–4 人日（核心逻辑 1 人日 + 适配 2 人日 + 回归 1 人日）。

**潜在风险与规避**：
- 日志膨胀：沿用现有 8MB 切片 + delta 不落盘策略。
- 双写一致性：用 `try/finally` + 写入失败降级为内存缓存，不阻塞主流程。

#### O2 内核级工具把关流水线

**技术路径**：
1. 新增 `server/工具流水线.mjs`：`pre-execute → execute → post-execute` 三段，pre 阶段跑 `evaluateToolGate` + 审批策略 + 命令安全策略。
2. `agent.mjs` 的自定义工具定义全部走流水线：在 `defineTool` 的执行体外包一层 `withPipeline(toolDef, pipeline)`。
3. Pi 内置工具（read/write/edit/bash）通过 `session.setActiveToolsByName` 后的执行路径注入拦截器。

**预期收益**：S3 根治；硬门禁替代软提醒；为 O6 沙箱拦截做准备。

**资源投入**：~2–3 人日。

**潜在风险与规避**：
- 内置工具拦截点不确定：在 Pi `tool_execution_start` 事件路径做 pre-check，若 Pi 后续版本改事件需同步更新；用契约测试锁定行为。

#### O3 持久 Job 队列 + 重启恢复

**技术路径**：
1. 新增 `server/Job队列.mjs`：SQLite/JSON 文件持久化 `{ jobId, runId, status, checkpoint, createdAt, updatedAt, result }`。
2. Run 从 HTTP 生命周期解耦：`POST /api/agent/prompt` 变成"入队 + 返回 jobId"，Run 后台执行。
3. 启动时自动扫描 `status=running` 的 Job，按 `checkpoint` 重放上下文。
4. 新增 `GET /api/jobs/:id` 进度查询端点。

**预期收益**：S4 根治；长任务可恢复；为 O9 DSH `ctx.jobs` 对齐做准备。

**资源投入**：~5–6 人日（队列 2 人日 + Run 解耦 2 人日 + 恢复逻辑 2 人日）。

**潜在风险与规避**：
- 后台执行的资源管理：设独立 limiter + 空闲回收。
- 重启后上下文不完整：强制要求每个 checkpoint 携带"上下文摘要 + 最后 N 条事件"，不依赖 Pi JSONL 重开。

#### O4 内核抽象 seam + KernelRegistry

**技术路径**：
1. 新增 `server/内核契约.mjs`：定义 `KernelAdapter` 接口 + `KernelSession` + 规范化事件 schema。
2. 新增 `server/内核注册表.mjs`：按 `kernelId` 路由，支持"默认 + 会话级覆盖"。
3. 新增 `server/PiKernelAdapter.mjs`：包装 `Pi运行时管理.mjs`，行为零变化。
4. `agent.mjs` 100 处耦合点逐步收敛到只通过 `KernelAdapter` 调用。

**预期收益**：S10 根治；O9 DSH 接入的前置条件；为"双内核共存"打通架构。

**资源投入**：~8–10 人日（接口 1 人日 + 适配器 3 人日 + 收敛 4–6 人日）。

**潜在风险与规避**：
- 收敛过程中的行为回归：每收敛一个子域跑对应 `test:*` 脚本，保持绿。
- 接口粒度不当：先按现有 Pi 接口 1:1 映射，后续迭代精化。

#### O5 近似 fork/replay 实现

**技术路径**：
1. 基于 O1 的追加式日志实现 `fork(fromSeq, newThreadId)`：复制日志 `seq ≤ fromSeq` 部分，指向新会话。
2. `resume(fromThreadId, snapshot)`：从日志重建上下文摘要，注入到新会话的 systemPrompt。
3. 前端"分支对话"按钮基于 Run 日志的 `seq` 分叉。

**预期收益**：S5 近似解决；为协作式开发场景铺路。

**资源投入**：~3–4 人日。

**潜在风险与规避**：
- 等价性：fork 后的模型状态与原会话不完全等价（因 Pi 无原生 fork），在 UI 明示"分支对话"而非"精确快照"。

#### O6 应用层沙箱 → Sidecar 进程隔离

**技术路径**：
1. 引入 `server/沙箱侧车.mjs`：子进程模式（Node.js `child_process.fork`），执行 `bash/write` 工具调用。
2. 父进程通过 JSON-RPC 下发命令 + 接收结果，子进程仅在"白名单目录 + 白名单命令"范围内执行。
3. Windows 上因 OS 级隔离有限，叠加"命令安全策略 + 路径白名单 + 超时杀死"。

**预期收益**：S2 部分解决；风险隔离显著提升。

**资源投入**：~8–10 人日（侧车 3 人日 + 命令安全 2 人日 + Windows 适配 3–5 人日）。

**潜在风险与规避**：
- Windows 隔离不彻底：明确"Windows 上为应用层隔离，Linux/macOS 上为 OS 级隔离"，在 UI 提示。
- 侧车引入的启动开销：常驻模式，首次启动后保持存活。

#### O7–O10 其余优化项

| # | 技术路径 | 收益 | 投入 | 风险规避 |
|---|---|---|---|---|
| O7 | 高频 token 流改为采样落盘；事件幂等键 `runId+seq+toolCallId` | 存储量 ↓30% + 回放可靠 | 1 人日 | 采样策略可配置 |
| O8 | 上下文窗口预算化（token 用量事件 + 软/硬阈值 + 压缩前预警） | 上下文焦虑缓解 | 2–3 人日 | 与 Pi 原生压缩协同 |
| O9 | `DshKernelAdapter` 实现：`dsh --profile sdk` sidecar + JSON-RPC | 拿到沙箱/原生 fork/Jobs | 10–15 人日 | 先 P0 spike 验证 Go/No-Go |
| O10 | 业务能力抽象为 MCP server（Office/KB/地图/记忆），Pi+DSH 双内核消费 | 能力复用 + 内核中立 | 5–6 人日 | 用 `mcp管理.mjs` 既有基础设施 |
