# 技术架构分析与内核迁移（Pi SDK → DeepSeek Harness）可行性报告

- 日期：2026-10-14
- 审计基线：`open-plan@0.11.52`（`package.json`），内嵌 `@earendil-works/pi-coding-agent@1.1.0`
- 调研对象：本项目内核实现、`DeepSeek Harness（dsh）` 公开架构资料
- 性质：静态代码审计 + 公开资料对照，未改动业务代码、未启动服务、未执行真实模型调用
- 结论口径：文中"已确认"均来自代码/官方文档；"待验证"为需要跑原型才能确认的事项，不做既成事实陈述

## 0. 结论摘要（TL;DR）

1. **本项目当前的技术形态是"内嵌 Pi Runtime + 自研 Harness 控制平面"**，而不是"一个 Pi 前端"。Pi（`@earendil-works/pi-coding-agent`）负责 Agent 循环、模型运行时、会话 JSONL 与工具执行；真正承载业务价值的是本项目自研的 Run / 事件 / 产物 / 工作区 / 权限 / 知识库 / 地图 / Office 这一层。
2. **"Pi → DSH 换内核"不是一个 1:1 的替换动作**。Pi 是 **Agent Runtime（库）**，DSH 是 **完整 Harness（含自己的会话日志、工具流水线、沙箱、审批、调度、SubAgent、Web UI 与桌面端）**。DSH 同时覆盖了 Pi（内核）和本项目自研 Harness（控制平面）两层，两者在职责上重叠。
3. **不建议整体替换 Pi。** 全量替换需要把 Office / 知识库 / 地图 / 权限 / 产物 / 工作区等业务能力在 DSH 的插件体系里重建，等于重做一遍控制平面，且 DSH 处于**开发者预览（含 RC 版本，官方明示会有破坏性变更）**，风险与收益不匹配。
4. **"前后端各做一套内核管理"（双内核）在技术上可行，而且是比"整体替换"风险更低、收益更清晰的路径。** 做法是：把 Pi 抽象成一个可替换的 `内核适配器（KernelAdapter）`，先落地 `PiKernelAdapter`（等价于现有 `PiRuntimeManager`，行为不变），再新增 `DshKernelAdapter`（以 `dsh --profile sdk` 的 JSON-RPC 子进程为宿主），由 `KernelRegistry` 按项目 / 会话维度路由；前端把"内核"变成一个可见维度（能力徽标、差异化面板、统一事件投影）。
5. **真正的短板不在"内核"，而在"编排层的事实来源不唯一 + 权限/沙箱/任务恢复不硬"。** 这些短板 DSH 恰好有成熟范式（追加式会话日志、带把关的工具流水线、`ctx.sandbox` 沙箱与审批策略、原生 fork/resume/replay、jobs/webhook 调度），**可以"借鉴设计"而不必"替换内核"**。
6. **推荐路线**：不要替换内核 → 先做内核适配 seam（`KernelAdapter`）+ 事件规范化 → 再把 DSH 作为**第二个可选内核（feature flag / 项目级开关）**接入 → 用同一套评测集对比两个内核，数据说话后再决定默认内核。

## 2. DeepSeek Harness（dsh）架构特性与能力范围

### 2.1 定位

- DeepSeek AI 开源的 **Agent Harness**（智能体框架），MIT 协议，2026-08-13 发布开发者预览 v0.1；npm 包 `@deepseek-ai/dsh` 当前已到 **0.2.0-rc.2**（30 个版本）。
- 命令行 `dsh`，官方口号 **"Agent = Model + Harness"、"Everything is a plugin"**。
- 它**不是大模型、也不是单纯的聊天界面**，而是把模型、工具、工作区、权限、会话记忆、循环、调度等**全部做成可替换插件**的运行时底座。

### 2.2 Cordis 插件内核

- 底层框架是 [Cordis](https://github.com/cordiverse/cordis)：插件向共享 `ctx` 贡献**服务、类型化事件、可逆副作用**。
- **没有需要打补丁的特权内核**：扩展方式是"把插件挂载到其他插件旁边"，注册即副作用，插件卸载时自动撤销。
- **Profile / Bundle / Patch** 三层组装：`web / headless / sdk / sdk-minimal / acp` 是随发行版交付的 profile 模板；`dsh-base` 是共享第一层（模型适配器、工具、持久化、**沙箱与审批策略**、设置、凭据、遥测）；用 `cordis.patch.yml` 按 id 定位并替换/插入配置项，支持 HMR。
- 一句话：**换一个 provider 就能改变整个产品行为**，无需改源码。

### 2.3 关键子系统（`ctx` seam）

| 包 | 职责 | `ctx` 键 |
|---|---|---|
| `core/session` | **仅追加的 `SessionEvent` 日志** + 内存存储 | `ctx.sessions` |
| `core/system-prompt` | 提示词片段与工具 schema 组装 | `ctx.systemPrompt` |
| `core/tools` | **作用域化工具注册表 + 带把关的执行流水线**（`tools/pre-execute → execute → post-execute`） | `ctx.tools` |
| `core/agent` | `Agent` 接口、活跃 agent 注册表、`agent/*` 事件 | `ctx.agents` |
| `core/agent-loop` | 默认驱动器（turn/step 循环） | `ctx.agentLoop` |
| `llm/llm` | 消息/流式词汇表 + **LLM 适配器 seam** | `ctx.llm` |
| 其他 seam | `ctx.fs`（文件系统/策略）、`ctx.sandbox`（沙箱）、`ctx.shell`/`ctx.terminals`、`ctx.commands`、`ctx.jobs`（后台任务）、`ctx.webhookRuntime`（外部触发）、`ctx.goals`、`ctx.sessionTitle`、`ctx.sessionProjections`、`ctx.agentTeams`（实验性多 Agent） | — |

### 2.4 事件与轮次模型

- **三类事件域**：会话事件（持久，`session/event`，追加到日志）、Agent 事件（`agent/*`，携带活跃 Agent：inbox/step/state/request/verification/续跑）、能力事件（`fs/*`、`tools/*`、`telemetry/*`，用于挂策略与适配器）。
- **轮次流程**：一个 **step** = 一次模型请求 + 它调用的工具；一个 **turn** 包含 0~N 个 step。扩展点是 waterfall 事件 `agent/pre-step`、`agent/request`、`llm/stream`、`tools/pre-execute|execute|post-execute`；`agent/turn-stopping` 是 serial 停止事件。
- **"模型可见即已记录"**：每个模型请求都能从会话日志重建；`deriveMessages()` 从日志投影出模型历史。
- **一次运行全程可追溯**：system prompt、reasoning、工具调用与结果、SubAgent 调度、每次上下文注入都进追加式日志；Trajectory 视图按来源查看，**resume / fork / search / replay 全部基于同一事件流**。

### 2.6 集成 / 嵌入面（决定"能不能当第二个内核用"）

这是本次调研最关键的发现——**dsh 提供的是 CLI 启动器，但同时提供 SDK profile**：

| 入口 | 用途 |
|---|---|
| `dsh web` | 启动自带 Web UI（默认 `127.0.0.1:3080`） |
| `dsh --profile sdk` | **以 JSON-RPC over stdio 服务 SDK 客户端，直到 shutdown/disconnect** |
| `dsh --profile sdk-minimal` | 同上，但用最小独立 Agent 树 |
| `dsh --profile headless "job"` | 运行一次持久会话、打印最终答案、退出 |
| `dsh --profile acp` | 面向自动化客户端的 ACP stdio 服务 |
| `dsh plugin --profile <name> <pnpm args>` | 管理 profile 插件（转发 pnpm） |
| `--dump-config` / `--dump-config-schema` | 打印/校验组装后的插件树 |

- **TypeScript SDK** 会解析同版本 `dsh` 依赖并选择 `sdk` profile；**Python SDK** 运行时 wheel 内部启动 `dsh --profile sdk`。
- `@deepseek-ai/dsh/profile-boot` 导出把 profile 生命周期交给 **Desktop host**（Electron 用 Node IPC + 私有 profile 承载完整 Web 应用）。

> **结论**：dsh 可被"外部宿主"驱动——最现实的嵌入方式是把 `dsh --profile sdk` 当作**子进程 sidecar**，宿主通过 JSON-RPC 下发创建会话/发送/取消等命令并消费事件流。这与本项目 `docs/plans/2026-09-09` 中"阶段五：Agent Runtime 进程隔离"的设想**同构**。

### 2.7 成熟度与限制（必须计入风险）

- 官方明示处于**开发者预览**，**"未来将出现破坏兼容性的变更"**；当前可装版本为 `0.2.0-rc.2`（Release Candidate）。
- 有 **82 个依赖**，体量与供应链面显著大于 Pi。
- 它自带完整 Web UI 与桌面端（Electron），**产品主张较强**——直接当"内核"用会把它的控制平面（会话日志/工具流水线/沙箱/审批/UI）一并带进来，与本项目自研 Harness 形成**双控制平面**。
- 文档主要为中英文官方站；插件生态新（`dsh-plugin` topic）。
- 沙箱在 Windows 上的可用性、以及 JSON-RPC SDK 客户端的具体 JS API，**本报告未验证，需原型 spike 确认**。

## 3. 能力匹配度对比

### 3.1 结构对照（最重要的一张图）

```
本项目当前形态                         DSH 形态
┌──────────────────────────┐          ┌──────────────────────────┐
│ 自研 Harness 控制平面      │          │ DSH 自带控制平面          │
│ Run/事件/产物/工作区/权限  │  ←重叠→  │ 会话日志/工具流水线/沙箱/  │
│                             │          │ 审批/调度/SubAgent/Web UI │
├──────────────────────────┤          ├──────────────────────────┤
│ Pi Agent Runtime（进程内库）│  ←重叠→  │ core/agent + agent-loop  │
│ 循环/模型/会话/工具        │          │ 循环/llm seam/ctx.tools  │
└──────────────────────────┘          └──────────────────────────┘
        ↑ 替换内核 = 同时触达这两层，不是只换下面那层
```

Pi 是"运行时库"，DSH 是"完整 Harness"。因此"换内核"的语义有三种，必须区分：

| 语义 | 含义 | 可行性 |
|---|---|---|
| A. 全量替换 | DSH 接管内核 + 控制平面 + UI | 低（等于重做产品，且丢掉 Office/KB/地图前端） |
| B. 仅换运行时 | 用 DSH 的 loop/模型/会话替代 Pi，保留自研 Harness | 中低（DSH 的控制平面难以剥离，需大量适配） |
| C. 双内核共存 | 两个内核都在，按维度路由，Harness 唯一权威 | **中，推荐** |

### 3.2 能力矩阵

| 能力维度 | 当前项目（Pi + 自研 Harness） | DSH | 成熟 Harness 标准 | 差距判断 |
|---|---|---|---|---|
| Agent 循环 | Pi `session.prompt` 驱动 | `agent-loop`，turn/step 显式建模 | 显式轮次/步骤状态机 | 项目侧轮次治理较隐式 |
| 会话日志 | Pi JSONL；`SessionManager` | **追加式 SessionEvent 日志**，模型可见即记录 | 追加式、可重放 | 项目侧缺"模型可见即记录"的强一致 |
| fork / resume / replay | fork 靠复制 JSONL；`nativeFork=reserved`；重开+提示词恢复 | **原生** fork/resume/search/replay（同一事件流） | 原生分支与回放 | **明显差距** |
| 工具注册 | `defineTool` + `customTools` 一次性注入 | `ctx.tools` 作用域注册 + **pre/execute/post 把关流水线** | 带策略的工具流水线 | 项目侧工具策略靠 `setActiveTools` 收缩 |
| 沙箱 / 进程隔离 | 无沙箱（Pi 非 Sandbox）；仅应用层审批/命令安全策略 | `ctx.sandbox` + `fs/*` 策略 + base 内置审批 | 真正的隔离边界 | **明显差距** |
| 权限 / 审批 | `审批策略.mjs` 应用层，部分工具未强制 | 审批策略属于 base，`tools/*` 可拦截 | 内核级可拦截 | 项目侧介入点不够硬 |
| 后台任务 / 调度 | Run 是同步 HTTP 内执行；无持久 Job；进程重启标 `recovering` | `ctx.jobs`、`ctx.webhookRuntime`、调度 | 持久队列 + 可恢复 Job | **明显差距** |
| SubAgent / 多 Agent | 单个只读子会话（120s 超时） | SubAgent provider + 实验性 Agent Teams | 可继续子 Agent + 团队 | 差距 |
| 上下文压缩 | Pi 原生压缩（reserve 16384 / keep 20000），未知模型回退估算 | 日志投影 + prompt 组装 seam | 预算化上下文管理 | 接近，但项目侧预算治理未完成 |
| 模型/供应商 | Pi 内置 33+ 供应商、1142 模型 + 导入管线 | `ctx.llm` 适配器 seam | 通道化能力协商 | 项目侧管线强，但绑死 Pi |
| 运行模式 | Chat / Office / Agent 三模式（靠工具白名单近似） | Standard/Code/Minimal/Creator | 能力预设 | 项目侧已接近，DSH 更彻底 |
| 可观测 / 轨迹 | `运行轨迹`/`运行展示投影`，事件持久化到 `.oaw/events` | Trajectory 视图，来源可查 | 全程可追溯 | 接近，DSH 更规范 |

**匹配度小结**：在"面向 Office/KB/GIS 的领域工具 + 中国式模型供应商接入 + 三栏工作台"上，**本项目明显强于 DSH 开箱能力**；在"内核级沙箱、原生 fork/replay、持久 Job 调度、工具把关流水线、SubAgent"上，**DSH 明显强于当前项目**。

## 4. 现有模型编排短板 vs 成熟 Harness 标准能力

结合 `Proma与Pi驱动Harness工程管理调研报告.md` 与代码审计，当前编排层的短板按"是否属于内核、是否可自研解决"分层：

| # | 短板 | 现象 | 归属 | DSH 是否有范式 | 自研能否解决 |
|---|---|---|---|---|---|
| S1 | **事实来源不唯一** | 会话有 Pi JSONL/工作台目录/前端 localStorage 多份；工作区 `cwd` 与 Pi `cwd` 可能不一致 | Harness | 追加式日志单一事实源 | 能（P0，最该做） |
| S2 | **无沙箱/进程隔离** | Pi 是进程内库，bash/write 无 OS 级隔离；Runtime 子进程化（阶段五）未做 | 内核+Harness | `ctx.sandbox` | 部分能（Sidecar/独立进程） |
| S3 | **工具权限不是硬门禁** | 模式切换靠提示词+工具白名单，非内核级拦截 | 内核 | `tools/*` 把关流水线 | 能（在项目侧做 pre-execute 门禁） |
| S4 | **无持久 Job / 重启恢复** | Run 绑 HTTP 生命周期，重启后标 `recovering`，靠"重开+继续提示" | Harness | `ctx.jobs` | 能（持久队列+checkpoint） |
| S5 | **fork/replay 非原生** | `nativeFork=reserved`，fork 靠复制 JSONL | 内核 | 原生 | 部分能（近似，等价性差） |
| S6 | **无 token 级 checkpoint** | 恢复=重开 JSONL + 提示词 | 内核 | 日志重放 | 难（受 Pi 限制） |
| S7 | **SubAgent 能力弱** | 单只读子会话、120s | 内核 | SubAgent/Agent Teams | 能（应用层多会话编排） |
| S8 | **上下文预算治理未完成** | 阶段六待执行；现主要依赖 Pi 原生压缩 | 内核+Harness | 日志投影 | 能 |
| S9 | **事件协议持久化/幂等不完整** | 阶段四已部分落地（`.oaw/events/事件流.jsonl`），高频 token 流未全持久化 | Harness | session/event 单一流 | 能 |
| S10 | **内核绑定过深** | `agent.mjs` ~100 处 Pi 耦合，无内核抽象 | 架构 | 插件 seam | 能（就是本报告要做的 seam） |

**关键洞察**：S1/S3/S4/S9/S10 属于 **Harness 层**问题，**无论换不换内核都要解决**；S2/S5/S6/S7 才真正受益于 DSH 的成熟范式。换句话说——**"编排层的短板"主要不是因为 Pi 不行，而是因为项目自身的 Harness 还没收敛。** 这也是"先做 seam、再谈换内核"的核心依据。

## 5. 技术迁移可行性评估

> 成本以"复杂度等级 + 涉及面 + 耦合点数量"表达，不给日历工期。

### 5.1 迁移成本（按工作包）

| 工作包 | 涉及面 | 复杂度 | 说明 |
|---|---|---|---|
| 定义内核抽象 `KernelAdapter` + `KernelRegistry` | `server/` 新增 2 模块，改动 `agent.mjs`/`index.mjs` 调用点 | 中—高 | 需先把 `agent.mjs` ~100 处 Pi 耦合收敛到适配层 |
| 事件规范化层（Pi 事件 ↔ DSH 事件 → 统一 schema） | 新增 1 模块 + `agent.mjs` 事件转译 + `事件注册表.mjs` | **高** | 两者事件模型差异大（见 6.1） |
| `PiKernelAdapter`（等价封装现有能力） | 包装 `Pi运行时管理.mjs` | 中 | 目标：行为零变化，作为基线 |
| `DshKernelAdapter`（sidecar JSON-RPC） | 新增 1 模块 + 子进程生命周期 + 事件桥 | **高** | SDK JS 客户端 API 需 spike 确认 |
| 业务工具桥接（Office/KB/地图/记忆） | `mcp管理.mjs` 复用 + 部分插件化 | **高** | 首选 MCP 桥接，避免重写 |
| 配置/凭据/模型通道统一 | `Pi配置管理.mjs` → 通道层 | 中 | DSH 用 `$DSH_HOME`，Pi 用规聚目录 |
| 会话存储并存与迁移 | `SessionManager` vs DSH JSONL v0/v1 | 中 | 不做双向迁移，按 `kernelId` 并存 |
| 前端内核维度（选择器/能力徽标/差异化面板/统一投影） | `SettingsPanel`/`IntegrationsCenter`/`ChatPanel`/`api.js` | 中 | 主要是"条件渲染 + 投影适配" |
| 回归：既有 `test:*` 脚本（近 50 个）保持绿 | `scripts/` | **高** | 事件/工具/恢复类脚本对内核敏感，必须双内核各跑一遍 |
| spike：DSH 嵌入面 + Windows 沙箱 + 模型复用 | 一次性验证脚本 | 中 | **必须先做，决定 Go/No-Go** |

### 5.2 风险点

| 等级 | 风险 | 说明与缓解 |
|---|---|---|
| 高 | **DSH 版本不稳定** | 开发者预览 + RC；官方明示破坏性变更。缓解：适配器隔离 + 版本锁定 + profile patch 固化 |
| 高 | **双控制平面** | DSH 自带会话日志/工具/审批，与自研 Run/事件/产物冲突。缓解：**明确 Harness 层为唯一权威**，DSH 只当执行引擎 |
| 高 | **嵌入面不确定** | `--profile sdk` JSON-RPC 的 JS 客户端、事件订阅协议细节未验证。缓解：P0 spike 先行 |
| 高 | **业务工具重写风险** | Office/KB/地图工具是核心资产。缓解：优先走 MCP 桥接（项目已支持 MCP），避免 DSH 内重写 |
| 中 | 沙箱 OS 兼容 | `ctx.sandbox` 在 Windows 的可用性未知。缓解：spike 验证；不可用则退化为应用层策略 |
| 中 | 模型通道重配 | 现有 33 供应商/1142 模型的导入管线绑定 Pi。缓解：抽 `ModelChannelManager` 作为独立层，两内核共用 |
| 中 | 性能/体积 | DSH 82 依赖 + 子进程常驻。缓解：按需启动、空闲回收、资源预算 |
| 中 | 学习/维护成本 | Cordis 插件模型需要团队学习曲线。缓解：先用 SDK profile 黑盒接入，不深入插件开发 |
| 低 | 许可 | DSH 为 MIT；Pi 许可证需另行核对后再决定分发形态 |

### 5.3 三种路线对比

| 路线 | 内容 | 收益 | 风险 | 建议 |
|---|---|---|---|---|
| A 全量替换 | 用 DSH 替换内核 + 控制平面 | 一次到位、拿到全部 DSH 能力 | 极高（重做产品、丢前端、RC 不稳定） | 不推荐 |
| B 仅换运行时 | DSH 当内核，保留自研 Harness | 拿到沙箱/原生 fork | 高（控制平面难剥离、适配量大） | 暂不推荐 |
| **C 双内核共存** | 内核抽象 seam + Pi 默认 + DSH 可选 | 增量、可回退、可对比 | 中（主要是 seam 与事件规范化） | **推荐** |

### 5.4 分阶段实施路径（推荐路线 C）

**P0 — Spike 与可行性闸门**（先做，不投入主代码）
- 一次性脚本验证：`npx @deepseek-ai/dsh --profile sdk` 能否被子进程驱动、JSON-RPC 是否可下发 prompt 并消费事件流；
- 验证 DSH 能否复用现有模型凭据（`ctx.llm` 适配器指向同一 baseUrl/key）；
- 验证 Windows 上 `ctx.sandbox` 行为；
- 产出 Go/No-Go 结论。**若 P0 不通过，只保留"借鉴 DSH 设计"，不做双内核。**

**P1 — 内核抽象 seam（行为零变化）**
- 新增 `server/内核契约.mjs`（`KernelAdapter` 接口 + 规范化事件 schema + 能力描述符）与 `server/内核注册表.mjs`（`KernelRegistry`）；
- 把 `Pi运行时管理.mjs` 包装为 `PiKernelAdapter`；
- `agent.mjs` 的 ~100 处 Pi 耦合改为只通过内核契约调用；
- 验收：全部既有 `test:*` 保持绿，功能与行为不变。

**P2 — DshKernelAdapter（sidecar）**
- 新增 `server/DshKernelAdapter.mjs`：以 `dsh --profile sdk`（或 headless）为子进程，JSON-RPC 下发命令、订阅事件、桥接为规范化事件；
- 业务工具优先通过 **MCP** 暴露给 DSH（复用 `mcp管理.mjs`），避免重写；
- 子进程生命周期：健康检查、崩溃退避重启、有序关闭、空闲回收。

**P3 — 双内核路由与前端可见**
- `kernelId` 成为 Workspace / Profile / Session / Run 的一个维度；API 与 SSE 携带 `kernelId`；
- 前端：设置页内核选择器、会话/运行详情能力徽标（内核名/版本/能力）、差异化面板（Pi 扩展中心 ↔ DSH Trajectory/插件视图）条件渲染；
- 统一 `运行展示投影.js` 消费规范化事件，聊天主界面不因内核而变。

**P4 — Harness 权威化与能力对齐**
- 明确 **Run / Event / Artifact / Workspace / Permission 由自研 Harness 唯一权威**，DSH 的会话日志作为"内核内部视图"可选展示（Trajectory）；
- 把 DSH 的审批/沙箱语义映射到项目 `审批策略.mjs`（同一 UI 入口，两套后端策略）；
- 借鉴 DSH 的"追加式日志""工具把关流水线""jobs 调度"补齐 S1/S3/S4/S9。

**P5 — 评测与决策**
- 用同一评测集（规划报告生成、Office 审校、GIS 分析、长任务恢复、断网重连）在两个内核上跑；
- 指标：工具调用成功率、首字延迟、终态延迟、恢复正确性、费用、可复现性；
- 依据数据决定默认内核与是否扩大 DSH 占比。

### 5.5 预期能力提升

| 维度 | 引入 DSH 后可获得 | 是否只有 DSH 能给 |
|---|---|---|
| 沙箱 / 进程隔离 | `ctx.sandbox`、`fs/*` 策略、base 审批 | 是（Pi 无沙箱） |
| 原生 fork/resume/replay | 同一事件流的原生分支与回放 | 是 |
| 持久 Job / 调度 | `ctx.jobs`、`ctx.webhookRuntime` | 是（较难自研等价） |
| 工具把关流水线 | pre/execute/post 拦截 | 否（自研亦可） |
| SubAgent / Agent Teams | 可继续子 Agent + 团队 | 部分（自研可近似） |
| 运行模式 | Standard/Code/Minimal/Creator | 否（项目已有三模式） |
| 可观测 | Trajectory 来源可查 | 否（项目已有轨迹） |

**注意**：上表中"是"的部分，正是**只有换内核才能拿到**的能力；"否"的部分，**自研也能补齐**，不应作为换内核的理由。

## 6. 兼容性影响与适配方案

### 6.1 后端兼容性

| 兼容面 | 现状 | 换/加内核的影响 | 适配方案 |
|---|---|---|---|
| 会话存储 | Pi JSONL（`SessionManager.open/create`） | DSH 是 JSONL v0/v1（`session.vN.jsonl` + migration） | **不做双向迁移**；会话元数据加 `kernelId/kernelVersion`，按内核各存一份；恢复时按内核路由 |
| 事件流 | Pi 事件（`text_delta`/`tool_execution_*`/`turn_*`/`agent_end`） | DSH 事件（`session/event`、`agent/*`、`turn/start`、`step/*`、`assistant-stream`、`tool/*`） | **新增事件规范化层**：两内核 → 统一内部事件 → 现有 `事件注册表.mjs`/SSE 协议不变 |
| 工具 ABI | `defineTool` + `customTools`（Pi 形状） | `ctx.tools` 作用域注册（DSH 形状） | 业务工具抽象为"工具描述符 + 执行器"，Pi 侧走 `defineTool`，DSH 侧走 MCP 桥 |
| 工具白名单 | `setActiveToolsByName` | DSH 用 preset / 作用域 | 归一化为"能力策略"（`task.mjs:toolPolicyForMode`）→ 各内核各自落地 |
| 模型/凭据 | Pi `ModelRuntime` + 规聚目录 | DSH `$DSH_HOME` + `ctx.llm` | 抽 `ModelChannelManager` 统一供应商/凭据/能力，两内核共用同一份 |
| 压缩策略 | Pi 原生（reserve 16384/keep 20000） | DSH 日志投影 | 能力对齐：按内核选择压缩实现，暴露同一"上下文用量"事件 |
| 运行记录 | `.oaw/运行时记录.json` + `piPackageVersion` | 需加 `kernelId/kernelVersion` | 记录结构向后兼容扩展字段 |
| 中断/取消 | `session.abort()` + `isUserAbort` 语义 | DSH 取消语义不同 | 适配层统一 `abort` 契约，保留"用户中断 vs 故障"区分 |

**结论**：后端**最大的兼容风险不是 API，而是事件模型和工具 ABI**。只要先立"规范化事件 schema + 工具描述符"两个契约，其余都是路由问题。

### 6.2 前端兼容性

| 兼容面 | 现状 | 影响 | 适配方案 |
|---|---|---|---|
| 对话主界面 | 消费 SSE 规范化事件 + `运行展示投影.js` | 只要事件规范化，**主界面几乎零改动** | 保持 `运行展示投影.js` 为唯一投影入口 |
| 内核字样 | 写死"Pi 内核/SDK 已加载"（`SettingsPanel.jsx:938`、`:1382`） | 显示错误 | 改为读 `kernelId/kernelVersion/能力` 动态渲染 |
| Pi 专属面板 | `IntegrationsCenter.jsx`（Pi 扩展）、Pi 供应商库 | 内核≠pi 时不应展示 | 按 `kernelId` 条件渲染 |
| 供应商/模型配置 | Pi 目录导入 | 通用化 | 走 `ModelChannelManager` 接口，两内核一致 |
| 任务中心/运行详情 | 基于 Run/事件投影 | 无影响 | 保持 Harness 权威 |

**结论**：前端是**低风险面**，因为它本来就和内核解耦（只认 HTTP/SSE）。真正要改的只是"内核可见性"相关的少量展示。

### 6.3 数据兼容性

- **会话数据**：按 `kernelId` 并存，**默认不迁移**。需要跨内核"继续对话"时，采用**新建会话 + 携带上下文摘要**的方式（与现有"恢复 Run"策略一致），不试图做 JSONL 格式互转。
- **运行/产物数据**：`.oaw/runs`、`.oaw/events`、成果 manifest 天然内核实无关（只存业务语义），**加 `kernelId` 字段即可**，历史数据缺失字段按"pi + 未知版本"降级显示。
- **配置/凭据**：规聚独立目录继续为唯一入口；DSH 的 `$DSH_HOME` 作为其内部实现细节，不暴露给用户。

### 6.4 适配方案总原则

1. **Harness 唯一权威**：Run / Event / Artifact / Workspace / Permission 只认自研层；内核产物是它的输入，不是它的替代。
2. **两个契约先行**：规范化事件 schema + 工具描述符。契约稳定后，内核可增可减。
3. **不追求内核间数据互转**：按 `kernelId` 并存，跨内核靠"上下文摘要续接"。
4. **业务能力走 MCP 桥**：Office/KB/地图/记忆等以 MCP 暴露，两内核都能用，避免重写。
5. **能力描述符可选**：每个内核暴露 `capabilities`（fork/replay/sandbox/jobs/…），前端据此决定入口可见性。

## 7. 回答核心问题：能否在前后端做"两套内核管理"？

**能，而且这是比"整体替换"更合理的路径。** 它等价于把"内核"从写死的实现，升级成"可插拔的运行时维度"。下面是可落地的设计。

### 7.1 后端双内核设计

```
                    ┌────────────────────────────────────────────┐
                    │  Harness 控制平面（内核无关，唯一权威）        │
                    │  Run / Event / Artifact / Workspace / Perm   │
                    └───────────────┬────────────────────────────┘
                                    │  只依赖「内核契约」
                    ┌───────────────▼────────────────────────────┐
                    │  内核契约 KernelAdapter（能力描述符 + 统一事件）│
                    └───────┬───────────────────────┬────────────┘
                            │                       │
              ┌─────────────▼──────────┐  ┌─────────▼──────────────────┐
              │ PiKernelAdapter         │  │ DshKernelAdapter            │
              │ （包装 Pi运行时管理.mjs） │  │ （驱动 dsh --profile sdk）    │
              │  进程内                  │  │  sidecar 子进程 + JSON-RPC   │
              └─────────────┬──────────┘  └─────────┬──────────────────┘
                            │                       │
              ┌─────────────▼──────────┐  ┌─────────▼──────────────────┐
              │ @earendil-works/pi-...  │  │ @deepseek-ai/dsh（Cordis）   │
              └────────────────────────┘  └────────────────────────────┘
                            │                       │
                    ┌───────▼───────────────────────▼───────┐
                    │  内核注册表 KernelRegistry（按维度路由）  │
                    │  kernelId 来源：项目 / 会话 / Profile     │
                    └───────────────────────────────────────┘
```

**内核契约（示意）**：

```ts
interface KernelAdapter {
  readonly id: "pi" | "dsh";
  readonly version: string;
  readonly capabilities: {
    nativeFork: boolean; nativeReplay: boolean; sandbox: boolean;
    jobs: boolean; subagents: boolean; checkpoint: boolean;
  };
  createSession(input): Promise<KernelSession>;
  resumeSession(input): Promise<KernelSession>;
  prompt(session, text, opts): Promise<void>;
  steer(session, text): Promise<void>;
  abort(session): Promise<void>;
  compact(session): Promise<void>;
  setModel(session, model): Promise<void>;
  setThinkingLevel(session, level): Promise<void>;
  setActiveTools(session, tools: string[]): Promise<void>;
  subscribe(session, onEvent: (canonicalEvent) => void): () => void; // 统一事件
  dispose(session): Promise<void>;
}
```

**规范化事件**（两内核都转成它，前端只认它）：沿用现有信封 `{ protocolVersion, eventId, sequence, runId, turnId, toolCallId, type, status, replayable, timestamp, payload }`，由适配层做映射（如 Pi `text_delta` 与 DSH `agent/assistant-stream chunk` 都映射为 `token`）。

**路由维度**：`kernelId` 挂到 **项目（Workspace/Project）** 为默认值，允许**会话级覆盖**。这样"规划项目走 Pi、实验项目走 DSH"或"同一项目里新旧会话各用一个内核"都能表达，且互不影响。

### 7.2 前端双内核设计

```
设置 · 模型与连接
  ┌ 内核 ──────────────────────────────────────────────┐
  │ 默认内核   ◉ Pi Agent（稳定，嵌入式）               │
  │            ○ DeepSeek Harness（实验，sidecar）      │
  │ 当前会话内核：Pi 1.1.0 · 能力：fork✗ replay✗ sandbox✗│
  └────────────────────────────────────────────────────┘
对话 / 任务中心
  · 运行详情徽标：内核名 + 版本 + 能力（用于解释"为什么没有分支按钮"）
  · 差异化面板：
      内核=pi  → 「Pi 扩展」「Pi 供应商库」可见
      内核=dsh → 「Trajectory 轨迹」「插件视图」可见，「Pi 扩展」隐藏
  · 主聊天区：完全不变（只消费规范化事件）
```

**前端改造原则**："内核只是运行详情里的一个字段 + 若干面板可见性开关"，**不新增第二套聊天逻辑**。这样既满足"两套内核管理"，又不会把前端复杂度翻倍。

### 7.3 需要先钉死的两个契约

1. **规范化事件 schema**（可直接复用 `Proma与Pi驱动Harness工程管理调研报告.md` 建议的事件信封）——它是前端"内核无关"的前提。
2. **工具描述符 + 能力策略**——它是"同一批 Office/KB/地图工具能在两个内核上跑"的前提，配合 MCP 桥即可避免重写。

### 7.4 验收要点（双内核）

- 切换 `kernelId` 后，**同一对话界面、同一 Run 投影**正常工作；
- 两个内核可以**并行**（各自独立的会话、子进程/进程内互不干扰）；
- 任一内核崩溃/超时，不影响另一内核与 Harness 层；
- 关闭 `dsh` 内核（feature flag off）后，**产品行为与今天完全一致**（可回退）；
- 既有 `test:*` 回归脚本在 `pi` 内核下全绿。

## 8. 建议与下一步

**结论**：
- **不建议整体替换内核**（路线 A/B）。DSH 是完整 Harness 而非可替换的运行时库，全量替换等于重做产品，且它处于开发者预览 + RC。
- **建议走双内核（路线 C）**：先把"内核"抽象成 seam（这一步无论换不换内核都值得做），再让 DSH 作为**第二个可选内核**接入，Harness 层保持唯一权威。
- **最该先做的不是"换内核"，而是把自研 Harness 的既知短板补硬**（事实来源唯一、工具硬门禁、持久 Job、事件单一流），这些问题 DSH 恰好有成熟范式，**先"借鉴设计"性价比最高**。

**下一步（按顺序）**：
1. **P0 spike**：验证 `dsh --profile sdk` 的子进程驱动与事件订阅、Windows 沙箱、模型凭据复用 → 产出 Go/No-Go。
2. **P1 seam**：落地 `内核契约.mjs` + `内核注册表.mjs`，把 `Pi运行时管理.mjs` 包成 `PiKernelAdapter`，行为零变化。
3. 在 P1 基础上再决定是否进入 P2（DshKernelAdapter）。
