# 第三段：任务"干完了却报失败"的根因（最高优先级发现）

**F20｜终态判定只看"模型调用是否干净收尾"，不看"客观产物是否已成"**
`run_0ce1624d`（22 分 42 秒 / 44 回合 / 输入 125k / 输出 101k）在界面上显示「本轮失败，可重试或调整要求」「处理失败，请重试」，而实际上**这一轮的活干完了**。终态事件序列如下（同一 Run）：

```
03:12:17.359  message_end        （assistant 最后一条消息正常结束）
03:12:17.413  turn_ended         toolCount=0
03:12:17.561  agent_error        {"message":"Stream ended without finish_reason","code":"PI_SETTLED_ERROR","category":"unknown","retryable":false}
03:12:17.691  assistant_final    {"text":"第六章已扩写完成并保存。…"}   ← 模型自己写的完整成功总结
03:12:17.810  agent_end          {"turns":44,"tools":45}
```

**根因链条**：
1. 供应商的流式响应**没有给出 `finish_reason` 就结束了**（流被截断）。同一 Run 里这个错误出现了两次：`02:57:31` 第一次触发 `agent_retry`（`willRetry:true`）自动重试，`03:12:17` 第二次被判定为**终态错误**（`retryable:false`）。
2. 工作台把它归入 `PI_SETTLED_ERROR` → **直接按模型调用失败收尾**，Run 落 `failed`。
3. 但客观证据全部指向成功：`assistant_final` 是完整的完成报告、产物已写盘并通过容器校验（`artifacts_validated: passed`、`verificationStatus: "passed"`、8,166,551 字节）。
4. 失败路径**不会执行产物发布**（`publishStagedRun` 只在 `completed` 时跑）→ 界面出现「交付产物 0 · 已确认 1」与「本轮失败」并存的矛盾。
5. 另外模型没有显式声明完成（无 `task_completed` 事件），于是结论卡用「失败状态 + 模型成功正文」拼出来 → 标题说失败、正文说完成。

**与既有修复的关系**：v0.11.44 修过同类问题（"中断不是故障"），但当时的判定收窄为「用户确实请求过中断 + 错误形如中断」，**没有覆盖"供应商流截断但产物已成"这一形态**。本次的判定缺陷更本质：**终态没有把"产物 + 验收"作为客观依据纳入**。

**产物本身完好（已核实）**：`F:\平湖投标\投标文件-第六章-多式联运体系功能协同研究.docx`，7.79MB，最后修改 11:09:12，与校验记录字节数一致。

**F21｜bash 与 officecli 是两套路径体系（同轮内并行）**
终态前一条 bash 的命令是 `cd /tmp/docker-desktop-root/run/desktop/mnt/host/f/平湖投标 && awk …`——**bash 实际运行在 Docker/WSL 挂载路径下**（`/tmp/docker-desktop-root/run/desktop/mnt/host/f/...`），而 officecli 走 Windows 原生路径（`F:\平湖投标`）。同一轮里 Agent 要在两套路径之间翻译同一个文件，这也是"暂存文件 officecli 读不到（F8）""写入落盘感觉无效"的温床。
