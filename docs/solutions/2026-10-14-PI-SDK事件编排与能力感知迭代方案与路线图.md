# PI SDK 事件编排与能力感知迭代方案 + 落地执行路线图

- 日期：2026-10-14
- 基线：`open-plan@0.11.52`，内嵌 `@earendil-works/pi-coding-agent@1.1.0`
- 范围：① Subagent 子代理能力；② 事件编排与能力感知升级；③ Office 场景链路优化与 Office CLI 内置可行性
- 性质：基于代码级审计 + 外部架构对照的**设计与实现路径**文档；不含代码改动
- 命名说明：本文"FDE Office CLI"指项目当前通过外部 `officecli` 二进制提供的 Office 文档能力（README 安装源 `https://d.officecli.ai/install.ps1`，二进制解析见 [workspace.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/workspace.mjs#L12-L24)）。若 FDE 另有专指，请指出，结论按同一实体处理。

## 0. 结论摘要

1. **Subagent 现状是"轻量只读子会话"，不是可用的任务编排**：`run_subagent` 只有 `scout/reviewer/planner` 三个字符串角色、只读、内存会话、120s 超时（[agent.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/agent.mjs#L2422-L2543)）；且 `subagent_start/update/end` **未登记进事件注册表**，因此**不落盘、不可跨会话回放**。
2. **能力感知层"算了但没接线"**：`运行预算.mjs`（硬预算/工具门禁/重复失败门禁）已实现但**全库无 server 侧 import**；当前生效的只有 `轮次预算.mjs` 的**软提醒文案**。`planTaskCapabilities` 只做"路由建议"，不构成硬约束。
3. **Office 链路是"外部二进制 + 全局并发 1 + 最长 120s"**：admission 阶段先 `checkOfficecli()` 预检，再经 `officeTool → runOfficecli → spawn` 串行执行；**即使是生成一份新 Word 也要等一个 Go 二进制冷启动**。
4. **完全内置 Office CLI 不可行，但"高频场景原生直写 + 高级能力降级 officecli"完全可行且收益大**：项目已具备原生 OOXML 能力（服务端 `docx`/`jszip`/`xlsx`，客户端 `docx-preview`/`pptxviewjs`）。文本撰写、材料生成、PPT 初稿这三类高频场景可以做到**零外部依赖**；图表、透视表、Morph 动画、修订跟踪、高保真渲染等长尾仍需 officecli。
5. **推荐路线**：借鉴 **DSH 的"seam + 追加式事件 + 工具把关流水线"** 与 **MiniMax Agent Team 的"Leader/Worker/Verifier + 对抗式验收 + 流水线式文档生成"**，在 PI SDK 之上做**编排层**增强，而不是改 Pi 内核。

### 1.2 事件编排现状

```
事件注册表.mjs  ──(唯一事实来源)──►  事件协议.mjs（通道/代际/分层）
        │                                   │
        └────────► 事件存储.mjs ◄────────────┘
             (.oaw/events/事件流.jsonl、写锁、8MB 切片、内存窗口 20000)
```

- **信封两套**：通道/SSE 事件 `{ id, type, at, streamId, protocolVersion, data:{...runId} }`；落盘 Store 事件 `{ eventId, seq, at, clientId, threadId, runId, type, data }`。
- **落盘白名单**：仅注册表 `persist:true` 的类型；`token/thinking/tool_output/stats/...` 不落盘（正确，避免洪水）。
- **通道淘汰策略**：超 4000 条时**优先淘汰最早的 delta**，保生命周期事件（[事件协议.mjs#L48-L56](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/%E4%BA%8B%E4%BB%B6%E5%8D%8F%E8%AE%AE.mjs#L48-L56)）。
- **Pi → 前端事件映射**全量清单见 [agent.mjs#L2592-L2867](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/agent.mjs#L2592-L2867)（`agent_started`/`turn_started`/`token`/`thinking`/`tool_call_progress`/`tool_start`/`tool_output`/`tool_end`/`message_start`/`message_end`/`stats`/`agent_turn_end`/`context_compacting`/`agent_retry`/`assistant_final`/`agent_end`/`agent_error`/`aborted` …）。

### 1.4 Office 链路现状

```
planTaskCapabilities → routing.officecli = "preferred"
        │
admission: if officecli preferred → await checkOfficecli()   ← 预检（缓存 60s/15s）
        │                                 ↑ 失败即抛 OFFICE_PREFLIGHT_FAILED
officeTool(args)  ← 工具参数只有一个字符串 args
   parseArgs → validateOfficecliArgs(工作区相对路径)
   → requireToolApproval(写操作) → acquireWriteLockWithRetry
   → materializeStagedReferences → ensureOfficeOutputDirs
   → runOfficecli → spawn(officecli, {cwd, env: OFFICECLI_MAX_DOM_ELEMENTS=8e6})
        └─ officeLimiter.run(...)  ← 全局并发 = 1（OAW_MAX_OFFICECLI）
        └─ 120s 超时；占用冲突自动 close 后重试一次
   → 结果文本回流 + 事件 officecli_failed / artifact_materialized
```

## 2. 外部参考与可迁移设计

### 2.1 DeepSeek Harness（DSH）

| DSH 机制 | 说明 | 对本项目的可迁移点 |
|---|---|---|
| Cordis **seam**（Service Definition / Provider / Consumer） | 每项能力都是可替换三件套 | 把"编排器 / 内核 / 工具 / 存储"都做成 seam，便于演进 |
| **追加式会话日志**（模型可见即记录，`deriveMessages()` 投影） | fork/resume/search/replay 都基于同一事件流 | 把 `subagent_*` 纳入可回放事件；Run 事件作为唯一事实来源 |
| **工具流水线把关** `tools/pre-execute → execute → post-execute` | 策略在工具真正执行**前**拦截 | `运行预算.mjs` 的 `evaluateToolGate` 接到 `tool_execution_start` 之前 |
| **`ctx.sandbox` + `fs/*` 策略** | 真正的隔离与文件策略 | 子代理/写入工具的路径与权限统一经 WorkspaceBroker |
| **Subagent 提供方**（同一接口下从"新建子 agent"到"委派给另一产品"） | 子代理是可替换 seam | 子代理执行器抽象为 `SubagentProvider` |
| **`ctx.agentTeams`**（持久 roster、任务状态、inbox 消息） | 多 Agent 协作的持久化形态 | Leader/Worker roster 用事件持久化，而非仅内存 |
| **`ctx.agents.create({ sessionId, seed, meta:{ parentSession, seedLength } })`** | 在轮次边界 fork | 子代理可从父会话某边界"播种"上下文 |
| `ctx.jobs` / `ctx.webhookRuntime` | 后台任务与外部触发 | Office 长任务异步化参考 |

### 2.2 MiniMax MCode / Agent Team

**CLI 侧（MCode）**：Session 支持 create/search/resume/**fork**/**rewind**/compact/export；`/steer` 指导当前轮、`Alt+Enter` 排队；**Plan Mode** 只控制规划不改权限；权限独立分层（Ask/Auto/Full/Off）；**Goal** 跨 Turn 保留持久目标并可设 **Token 预算**；**`/btw` `/side` 临时侧会话**继承主会话最近提交边界、主任务继续跑；Headless 支持 JSON/事件流输出。

**Agent Team 侧（核心可借鉴）**：
- **三角色**：**Leader**（把用户目标转成任务结构）→ **Worker**（执行子任务，各自不同工具/上下文/输出要求）→ **Verifier**（把"做完了"变成"可交付"，与 Worker 构成**对抗关系**）。
- **快速响应**：主 Agent 先秒回"已接收 + 目标确认 + 后台拆分执行"，关键节点才汇报（任务开始/阻塞/待决策/完成）。
- **确定性代码驱动的 Agent 循环**：不是让模型自己决定协作，而是用代码逻辑编排。
- **上下文隔离**是质量的主要来源；角色越清晰，Worker 输出越可复用/可比较/可检查。
- **流水线式 Office 文档生成**（直接对应本项目 Office 场景）：
  `Planner（目标+结构）→ Writer（正文）→ Formatter（版式+文件对象）→ Evaluator（独立核查内容/格式/文件完整性）`，
  把"一次性文本生成"变成**类 CI/CD 构建流水线**：**每步产出中间产物、每步有检查**。

### 2.3 共性设计原则（本方案采用）

1. **编排用代码，不用模型自治**（MiniMax）——角色、并发、门禁、验收由确定性逻辑驱动。
2. **每步产出可检查的中间产物**（MiniMax 流水线）。
3. **执行前把关，而非执行后提醒**（DSH `pre-execute`）。
4. **事件是唯一事实来源，且模型可见即已记录**（DSH 追加式日志）。
5. **能力 = 可替换 seam**（DSH Cordis）。

## 3. Subagent 子代理能力：架构与实现路径

### 3.1 目标与原则

- 从"只读助手"升级为**可编排的角色化子代理**：支持读写分级、并发、结果对账、可持久回放。
- **不改 Pi 内核**：全部建立在 `piRuntimeManager.createSession` + `session.subscribe` + `setActiveToolsByName` 之上（现有子会话机制已证明可行）。
- **变更可回退**：保留现有 `run_subagent` 语义，新能力以新模式/新工具并存。

### 3.2 目标架构

```
                       ┌──────────────────────────────────────────┐
                       │  子代理编排器 SubagentOrchestrator          │
                       │  （确定性代码：拆分 / 调度 / 对账 / 门禁）      │
                       └───────┬───────────────┬──────────────┬───┘
              role=scout/reviewer/planner  │        │          │
                       ┌───────▼───────┐ ┌─────▼─────┐ ┌──────▼──────┐
                       │ Leader(主)    │ │ Worker×N  │ │ Verifier×M  │
                       │ 规划/汇总      │ │ 并行执行   │ │ 对抗式验收   │
                       └───────┬───────┘ └─────┬─────┘ └──────┬──────┘
                               │               │              │
                     ┌─────────▼───────────────▼──────────────▼─────────┐
                     │  SubagentProvider seam（可替换执行器）              │
                     │  · PiChildSession（进程内子会话，沿用现有机制）        │
                     │  · 未来可换：独立进程 / 外部 Agent / DSH           │
                     └───────────────────┬───────────────────────────────┘
                                         │ 统一事件（纳入事件注册表）
                     subagent_planned / subagent_started / subagent_progress /
                     subagent_tool / subagent_result / subagent_verified / subagent_closed
```

**执行器 seam（`SubagentProvider`）**——对齐 DSH "同一接口下多种子代理实现"：

```ts
interface SubagentProvider {
  readonly kind: "pi-child" | "process" | "remote";
  run(input: {
    parentEntry, task, role, tools: string[], readOnly: boolean,
    workspace, seed?: { sessionId, seedLength }, budget, signal, emit,
  }): Promise<{ childId, status, output, artifacts, toolStats, usage }>;
  abort(childId): void;
}
```

### 3.3 与 PI SDK 的适配（复用现有可行机制）

| 能力 | PI SDK 落地方式 |
|---|---|
| 子会话 | `piRuntimeManager.createSession({ resourceLoader, sessionManager, settingsManager, customTools, tools })` |
| 上下文隔离 | `DefaultResourceLoader({ noExtensions/noSkills/noPromptTemplates/noContextFiles, systemPrompt })` |
| 上下文播种 | 子会话首个 user 消息内联"父任务简报 + 引用摘要"；**不继承父历史**（避免污染与膨胀） |
| 工具分级 | 按角色给 `tools` 白名单：`scout/reviewer` → `["read","grep","find","ls"]`；`worker` → 加 `officecli`/`write`（受审批）；`verifier` → 只读 + `view/query` |
| 并发 | 用现有 `AsyncLimiter`（`piRuntimeManager.agentLimiter`），为子代理开独立 limiter（默认 2–3），避免抢占主会话 |
| 预算 | 每子代理注入轮次/工具预算（复用 `运行预算.mjs` 逻辑，见 §4.2） |
| 超时/取消 | 保留 `Promise.race` + `signal` 联动；超时改**分级**（scout 60s / worker 180s / verifier 120s） |
| 流式回传 | 保留"节流 preview + 结构化 progress"，**不再逐 token 外发**；新增 `subagent_tool` 事件携带 `toolCallId` |
| 持久化 | 子会话可选 `SessionManager.create()`（落 JSONL）用于**可复现**，默认仍 `inMemory`（省盘） |

> 关键设计：**Leader/Verifier 由编排器（代码）担任**，而不是再开一个模型会话——对齐 MiniMax "确定性代码逻辑驱动的 Agent 循环"，成本可控、行为稳定。Worker 才是模型会话。

### 3.4 事件契约（补齐 G2 / G3）

在 [事件注册表.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/%E4%BA%8B%E4%BB%B6%E6%B3%A8%E5%86%8C%E8%A1%A8.mjs) 增补：

| 事件 | lifecycle | persist | 关键字段 |
|---|---|---|---|
| `subagent_planned` | ✅ | ✅ | `childId, role, task, tools[], budget` |
| `subagent_started` | ✅ | ✅ | `childId, role, model, seedRef` |
| `subagent_progress` | ✅ | ❌ | `childId, phase, activity, preview?(节流)` |
| `subagent_tool` | ✅ | ✅ | `childId, toolCallId, name, status` |
| `subagent_result` | ✅ | ✅ | `childId, status, output, artifacts[], toolStats, usage` |
| `subagent_verified` | ✅ | ✅ | `childId, verdict(pass/revise/fail), checklist[], notes` |
| `subagent_closed` | ✅ | ✅ | `childId, finalStatus, parentToolCallId` |

**强制约定**：子代理事件**一律带 `parentToolCallId`**（即父会话中 `run_subagent` 的 toolCallId），前端归约与 UI 一律按 `toolCallId` 定位，修复 G3。

配套修正：事件注册表测试的扫描正则需同时覆盖 `emitChild(...)` 变量传参路径（或在注册表侧提供 `assertRegistered(type)` 运行时断言）。

### 3.5 角色与能力矩阵

| 角色 | 目标 | 工具白名单 | 输出契约 | 是否模型会话 |
|---|---|---|---|---|
| `planner` | 拆解目标为任务结构 | 只读 | `{ tasks[], deps[], acceptance[] }`(JSON) | 可选（复杂任务时） |
| `scout` | 检索/读资料 | 只读 | 摘要 + 证据路径 | ✅ |
| `worker` | 执行子任务（写作/改文档/分析） | 按子任务给（含 officecli 需审批） | 中间产物（文件/表格片段） | ✅ |
| `reviewer` | 对抗式核查内容/格式/完整性 | 只读 + officecli `view/query` | `{ verdict, checklist[], issues[] }` | ✅ |
| `verifier`(流水线) | 交付前门禁（见 §5.2） | 只读 | 同上 | ✅ |

### 3.6 实现步骤（P0 → P2）

1. **P0（打地基，低风险）**
   a. 注册表增补 `subagent_*`（含 `parentToolCallId`）→ 落盘 + 回放；
   b. 前端 [运行展示投影.js](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/client/src/%E8%BF%90%E8%A1%8C%E5%B1%95%E7%A4%BA%E6%8A%95%E5%BD%B1.js) 增加子代理分支渲染（按 `parentToolCallId` 归到父工具卡下）；
   c. 注册表测试补 `emitChild` 覆盖。
2. **P1（角色化 + 工具分级）**：抽出 `SubagentProvider` seam + 角色定义表；`worker` 支持写工具（走审批/写锁）；超时分级。
3. **P2（并发编排 + 验收）**：`SubagentOrchestrator` 支持 fan-out（N 个 Worker 并行）、汇总、`verifier` 对抗核查与 `revise` 回环（最多 1 轮），全部以事件持久化 roster。

## 4. 事件编排与能力感知升级

### 4.1 能力计划 → 能力契约（G4）

现状 `planTaskCapabilities` 只给 `routing.officecli="preferred"`。升级为**可执行的能力契约**：

```ts
type CapabilityContract = {
  version: 2;
  mode: "chat" | "office" | "agent" | "review";
  capabilities: Array<{
    id: "document_read"|"office_write"|"office_generate"|"knowledge"|"map"|"skills"|"subagent";
    status: "required"|"preferred"|"not_needed";
    provider: "native"|"officecli";      // 新增：来源
    tools: string[];                      // 该能力允许的工具
    gate?: { approval?: boolean; budget?: { turns?; tools? } };
  }>;
  output: { expected: string[]; deliverable: boolean };
};
```

- 新增 `provider` 字段：把 §5 的"原生直写优先"变成契约的一部分，工具层据此路由。
- `emitChannelSafe(..., "capability_plan", contract)` 的时机**提前到 admission 之后、首个模型请求之前**，保证前端在首个 token 前拿到能力边界（修复时序竞争）。

### 4.2 硬预算与工具门禁接线（G5）

`运行预算.mjs` 的 `evaluateToolGate()` 应接到 **Pi 的 `tool_execution_start` 之前**（DSH `pre-execute` 范式）：

- Pi SDK 层：在 `customTools` 的执行体入口统一包一层 `withToolGate(entry, toolName, args, fn)`；
- 内置工具（`read/write/edit/bash`）与自定义工具**共用同一门禁**；
- 门禁结论发事件 `run_budget_notice`（软）/ `run_budget_blocked`（硬），前端可见；
- 硬预算命中：停止发起**新的**任务工具，允许一次受限收尾（与 [2026-09-30 计划](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/docs/plans/2026-09-30-001-%E5%89%8D%E7%AB%AF%E6%89%A7%E8%A1%8C%E6%B5%81%E6%96%87%E4%BB%B6%E4%BA%A7%E7%89%A9%E4%B8%8EHarness%E6%94%B9%E9%80%A0%E8%AE%A1%E5%88%92.md) 第 278 行一致）。

### 4.3 事件编排的准确性 / 顺序 / 幂等

| 优化 | 做法 |
|---|---|
| 归属准确 | 所有工具类事件以 `toolCallId` 为键（含子代理 `parentToolCallId`），前端归约不再"取最后一个工具块" |
| 顺序稳定 | 能力/模式/预算类"前置事实"事件在**首个 token 之前**发出；生命周期事件不被 delta 挤掉（已有策略，保持） |
| 幂等 | `runId + eventId` 去重（已有），补 `toolCallId` 维度 |
| 可回放 | 补齐 `subagent_*` 落盘；把"能力契约""预算结论"纳入持久类型 |
| 时延可视 | 沿用 `首字延迟.mjs`，新增子代理/Office 分段埋点（admitted → plan → preflight → tool_start → first_output → done） |

## 5. Office 场景专项优化

### 5.1 现状瓶颈（针对"文本撰写 / 材料生成 / PPT"）

1. **生成类任务也走重链路**：写一份新 Word/PPT 也要 `checkOfficecli` 预检 + spawn 冷启动（60s resident 之外仍是进程启动成本）。
2. **全局并发 1**：多文件任务被串行化（`officeLimiter` limit=1）。
3. **单次 120s 超时 + 大参数经 `--prop` 字符串**：易产生转义/长度问题（`office参数.mjs` 的手写分词即为此）。
4. **事件触发不够准**：`officecli_failed` 已在多处发，但"是否真的需要 officecli"由关键词/扩展名启发式决定，易误触发或漏触发。
5. **无 pptx 原生生成**，PPT 场景 100% 依赖外部二进制。

### 5.2 流程链路优化：Editorial Pipeline（借鉴 MiniMax 流水线）

把"一次性生成"改造为**每步有中间产物、每步有检查**的流水线：

```
Planner（目标+结构：大纲/页序/章节）
   │  中间产物：outline.json
Writer（正文：章节文本 / 幻灯片文本）
   │  中间产物：draft.md / slides.json
Formatter（版式+文件对象：样式、模板、页码、图表占位）
   │  中间产物：document.docx / deck.pptx
Evaluator（独立核查：内容覆盖、格式合规、文件可打开、结构完整）
   │  结论：pass / revise(→回 Formatter 一次) / fail
   └─ 通过 → 交付产物（Artifact）
```

- **每步发独立事件**（`pipeline_stage_started/finished`，登记注册表），前端展示为可折叠的阶段条；
- **Formatter 优先原生**（§5.5），Evaluator 复用现有 [成果验收.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/%E6%88%90%E6%9E%9C%E9%AA%8C%E6%94%B6.mjs)；
- 该流水线天然适合用 §3 的 `worker`（Writer/Formatter）+ `verifier`（Evaluator）实现。

### 5.3 事件触发准确性与响应速度优化

| 优化点 | 措施 | 预期收益 |
|---|---|---|
| 触发准确 | 能力契约新增 `provider`，把"生成新文档"与"精确编辑既有文档"分流；生成类不触发 officecli 预检 | 去掉无效预检与误触发 |
| 首字更快 | 生成类任务**不走** `checkOfficecli` 阻塞；预检改为**并行/惰性**（真正需要时再检） | admission 时延下降 |
| 冷启动消除 | 原生直写路径**不 spawn**，无进程启动、无 resident 60s 等待 | Office 生成任务显著提速 |
| 并发提升 | 原生路径不占 `officeLimiter`（limit=1 只约束 officecli 二进制）；officecli 仍保持 1 以免文件锁冲突 | 多文件任务并行 |
| 减少往返 | 批量写（`batch`/原生一次写多段）替代多次单条 `add/set` | 工具调用次数下降 |
| 锁竞争 | 原生路径按文件粒度加锁（复用 [写入协调.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/%E5%86%99%E5%85%A5%E5%8D%8F%E8%B0%83.mjs)），不占用 officecli 的共享冲突重试 | 失败率下降 |

### 5.4 完全内置 FDE Office CLI 的可行性

**结论：完全内置（1:1 复刻 officecli）不可行；"高频场景内置 + 长尾降级"可行。**

理由（基于 officecli 能力面）：它是覆盖 **docx/pptx/xlsx 三格式、L1 读取/L2 DOM 编辑/L3 原始 XML、图表/透视表/条件格式/迷你图/公式/修订跟踪/Morph 动画/SmartArt/OLE/3D/视频音频/图表动画/多语言 RTL 等**的单二进制工具（详见 [officecli SKILL.md](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/.claude/skills/officecli/SKILL.md)）。在 Node 里 1:1 复刻需要数年工程量，且渲染/动画部分依赖其自有渲染器。

**分层策略**（原生优先，officecli 兜底）：

| 场景 | 频率 | 方案 | 说明 |
|---|---|---|---|
| 新建 Word / 生成材料正文 | 高 | **原生**（`docx@9`） | 段落/标题/表格/图片/页眉页脚/样式；`docx` 库直接生成 |
| 生成 PPT 初稿 | 高 | **原生**（新增 `pptxgenjs` 或 jszip+OOXML 模板） | 标题页/要点页/图文页/表格页 |
| 读取文档内容做分析 | 高 | **原生**（`jszip`+XML / `xlsx`） | 已有 `context.mjs` 可复用 |
| Excel 读写/基础公式 | 高 | **原生**（`xlsx`） | 已有 |
| 精确修改既有文档（定位段落/run） | 中 | **原生**（jszip+XML）或 officecli | 结构化编辑原生可行；复杂样式继承建议 officecli |
| 图表/透视表/条件格式/迷你图 | 中低 | **officecli** | 复刻成本极高 |
| 修订跟踪 / 批注 / 找替换 | 中低 | **officecli** | 语义复杂 |
| Morph 动画 / SmartArt / 3D / OLE | 低 | **officecli** | 无原生替代 |
| 高保真渲染 / 截图 / PDF 导出 / watch | 中 | **officecli** | 依赖其渲染器 |
| 表单域 / 数字签名 / 加密 | 低 | **officecli** | 长尾 |

**覆盖率估算（按"高频场景调用次数"口径，非能力项口径）**：文本撰写/材料生成/PPT 初稿这三类可覆盖**大部分日常调用**为原生路径；长尾高级能力仍保留 officecli。**这是"大幅降低对外部二进制的依赖与冷启动"，不是"完全移除"**。

### 5.5 无外部依赖的原生编辑技术方案

**统一抽象**：新增服务端模块 `server/文档引擎.mjs`，对外提供与 officecli 同形的能力，但内部可路由：

```ts
// 与现有 officeTool 兼容的窄接口
interface DocumentEngine {
  capabilities(): { format: "docx"|"pptx"|"xlsx"; native: string[]; requiresCli: string[] };
  create(format, outPath, opts): Promise<Result>;                     // 原生
  read(path, { mode: "text"|"outline"|"json" }): Promise<Result>;     // 原生(jszip/xlsx)
  appendNodes(path, nodes): Promise<Result>;                          // 原生(docx/pptxgenjs)
  setText / setStyle / replaceText ...
  needsCli(op): boolean;                                              // 路由判定
  delegateToCli(op): Promise<Result>;                                 // 降级到 runOfficecli
}
```

**Word 原生**：服务端 `docx@9` 生成 `.docx`（已被 [notice.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/notice.mjs#L13) 使用）；读取/定位用 `jszip` 解 `word/document.xml`（已被 [context.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/context.mjs#L235-L242) 使用）。编辑既有文档的段落/run 可基于 XML 的 `paraId` 稳定寻址（对齐 officecli 的 `@paraId=` 思路）。

**PPT 原生**：引入 `pptxgenjs`（生成 slides/shapes/text/tables/charts 基础）或准备**模板 `.pptx` + jszip 替换占位**的轻方案；渲染继续用客户端 `pptxviewjs`。

**Excel 原生**：`xlsx@0.18`（已有）。

**一致性保障**：
- 原生产出与 officecli 产出统一经 [成果验收.mjs](file:///f:/Claude%20code%E6%9C%AC%E5%9C%B0%E6%96%87%E4%BB%B6/office-agent-web/server/%E6%88%90%E6%9E%9C%E9%AA%8C%E6%94%B6.mjs) 做完整性校验（ZIP 头/可解析/结构）；
- 工具对外**仍是 `officecli` 工具名**（对模型透明），内部按 `DocumentEngine.needsCli(op)` 路由；避免改动模型侧工具契约与既有测试断言。
- 降级策略：原生路径异常 → 自动回退 officecli（保留 `officecli_failed` 事件语义）。

### 6.2 技术实现要点（汇总）

1. **不改 Pi 内核**，全部在编排层（`agent.mjs` / `task.mjs` / `office.mjs` / 新模块）实现。
2. **事件是唯一事实来源**：新增/变更事件必须先登记注册表；工具类事件一律 `toolCallId` 归属。
3. **执行前把关**：能力契约 + 预算门禁在工具真正执行前判定，重提醒改为硬约束。
4. **原生优先、CLI 兜底**：对外工具名不变，内部分流，异常自动降级。
5. **编排用代码**：Leader/Verifier 由确定性逻辑担任，Worker 才用模型。
6. **每步留中间产物与检查**：流水线阶段可回放、可验收。
7. **可回退**：新能力以并存方式接入（feature flag / 模式开关），任一内核或 CLI 不可用时降级而非中断。
