# 第一阶段：基于 PI SDK 原生能力的优化方案（迭代优化版）

- 日期：2026-10-15
- 基线：`open-plan@0.11.52` + `@earendil-works/pi-coding-agent@1.1.0`
- 前置文档：[自研Harness对标分析与优化落地计划](./2026-10-15-自研Harness对标分析与优化落地计划.md)、[技术架构分析与内核迁移可行性报告](./2026-10-14-技术架构分析与内核迁移可行性报告.md)
- **硬约束**：所有优化逻辑完全基于 PI SDK 原生能力实现，**不引入任何新的外部依赖**（零新增 npm 包、零新增二进制）
- 证据口径：本文所有"SDK 已提供"结论均来自 `node_modules/@earendil-works/pi-coding-agent/dist/*.d.ts` 类型定义实读；所有"项目现状"结论均来自 `server/` 代码 grep 实证

---

## 0. 结论摘要

1. **核心发现**：Pi SDK 1.1.0 的实际导出面远大于项目当前使用面。此前架构报告中标注为"SDK 缺失/受限"的若干能力（会话树分支、上下文预算精确计算、工具执行包装、进程 RPC 模式、bash spawn 钩子）**在 SDK 中均已原生提供，项目侧未接入**。
2. 因此本阶段优化的主基调是 **"从自研近似升级为 SDK 精确实现"**，而非引入新依赖。11 个优化项全部零新增依赖。
3. 收益最大的三项：**U1 上下文预算精确化**（替换自研 token 估算）、**U3 原生会话树分支**（根治 S5 fork 缺口，此前评估为"受 Pi 限制难解决"，实际 SDK 已提供 `navigateTree`/`fork`）、**U2 工具单点拦截**（`ToolCallEventResult{block,reason,terminate}` 已实证，hard 模式不再全 Run 中断）。U5 进程隔离经评审修正（R6）为"bash 侧车执行 + 侧车基建"缩水路径（SDK RPC 命令集静态核验不含 customTools 注册，全量 sidecar No-Go），其侧车基建直接复用于第二阶段 DSH 适配。
4. 第二阶段（DSH 适配）的前提能力（事件规范化、sidecar 生命周期管理）由 U8 与 U5 在本阶段先行落地，使 DSH 适配改动面收敛到最小。

### 1.3 能力缺口对照结论

- 架构报告 §1.1 的 `nativeCheckpoint: "unsupported"` 判断**部分修正**：token 级 checkpoint 确实无，但**会话树级分支/导航原生可用**（U3），"恢复=重开+提示词"可升级为"树导航+分支摘要"。
- S2（无进程隔离）的解法优先级重排：**U5（Pi 原生 RPC sidecar）先于 DSH `ctx.sandbox`**——零新依赖、复用现有凭据/配置管线、且为 DSH sidecar 提供同构基础设施。

### U1 上下文预算治理精确化（P0）

**现状问题**：agent.mjs:3355 用 `estimatedFallbackThreshold` 估算阈值触发压缩提醒；无精确 token 计量，前端"上下文 N%"显示为估算值；压缩时机不可控（完全依赖 SDK 自动）。

**实现步骤**：
1. `Pi运行时管理.mjs`：新增 `session.getContextUsage()` 透传方法（进程内直调，无 IO）。
2. `agent.mjs` 事件转译层：在 `agent_turn_end` / `stats` 事件处调用 `getContextUsage()`，发出新事件 `context_usage`（需在事件注册表登记：`{ type: "context_usage", lifecycle: true, persist: false }`，高频不落盘，SSE 透传）。
3. 压缩决策：用 `calculateContextTokens(usage)` + `shouldCompact(tokens, model.contextWindow, DEFAULT_COMPACTION_SETTINGS)` 替换 L3355 自研估算；保留估算值作为 `getContextUsage()` 返回 undefined 时的 fallback（SDK 文档行为：非流式或极端情况可能无 usage）。
4. 前端 `ChatPanel.jsx` 上下文百分比按钮（e80"上下文 0"）消费 `context_usage` 事件的精确值。

**预期效果**：
- 上下文显示误差从估算级（±15-30%）降到精确级（usage 实测值）；
- 压缩触发时机与真实窗口对齐，避免"过早压缩丢上下文"或"过晚压缩触发 API 超限"两类故障；
- 为 U6 的压缩预警提供数据源。

**实现成本**：1.5 人日（后端 1 + 前端 0.5）。

**风险点**：① `getContextUsage()` 在部分供应商/非流式路径返回 undefined；② 旧会话 JSONL 无 usage 条目。
**规避**：保留现有估算逻辑作为 fallback 分支（当前代码不删除，仅调整优先级）；回归测试覆盖 usage 缺失路径。

### U2 工具把关流水线升级（P0）

**现状问题**：E02 门禁（agent.mjs:2966）挂在 Pi `tool_execution_start` 事件上——该事件是"通知"而非"拦截点"，硬预算命中只能 `abort()` 整个 Run（agent.mjs stopRunByBudget），无法**只拒绝单个工具调用并让模型继续**。这是与 DSH `tools/pre-execute` 的本质差距。

**实现步骤**：
1. 利用 Pi 扩展系统：新增 `server/Pi把关扩展.mjs`，实现 `ExtensionFactory`，在 `ToolCallEvent` 处理器中调用现有 `evaluateToolGate()`（运行预算.mjs 纯逻辑复用），返回 `ToolCallEventResult { block, reason, terminate }`（types.d.ts L1065-1073 已实证单工具拒绝语义）实现单工具级拒绝；`CustomToolCallEvent` 覆盖 customTools，内置工具走同名 `ToolCallEvent`——**统一入口**。拒绝时向会话注入一条系统提示"该工具调用被预算门禁拒绝，原因 X，请调整方案"。
2. ~~自定义工具经 `wrapRegisteredTools()` 包装~~（**评审修正 R5**：`wrapRegisteredTools(RegisteredTool[], ExtensionRunner)` 仅作用于扩展注册的工具，与 `createAgentSession({ customTools })` 注入路径类型不匹配，不可用）——customTools 拦截统一由第 1 步的 `CustomToolCallEvent` 承接。
3. 保留 agent.mjs:2966 的 `tool_execution_start` 门禁作为**兜底层**（防扩展未加载），并新增观测：扩展加载失败（`discoverAndLoadExtensions` 返回错误）时发 `agent_error` 级告警事件，避免兜底层静默接管而无人知晓（评审补充）。
4. 注册表新增事件 `tool_gate_denied`（persist: true），前端工具卡片可显示"被门禁拒绝"态。

**预期效果**：
- 单工具拒绝不再终止整个 Run——长任务在硬预算下的可用性提升（此前 hard 模式 = 全 Run 中断）；
- 审批/安全/预算三个策略点收敛为一条流水线，维护成本下降；
- 对齐业界"pre-execute 把关"标准。

**实现成本**：3 人日（扩展 1.5 + 包装改造 1 + 回归 0.5）。

**风险点**：① Extension 系统与现有 customTools 注入的兼容性（`noExtensions` 当前为 true——子会话禁用扩展，主会话未禁用，需验证扩展在主会话的加载路径）；② `ToolCallEventResult` 的拒绝语义需 spike 确认（拒绝后模型是否收到结构化反馈）。
**规避**：P0 阶段先做 1 个 spike 脚本（scripts/spike-tool-gate.mjs）验证扩展加载与拒绝语义，通过后再全量接线；子会话保持 `noExtensions`（子代理有自己的预算控制）。

### U3 原生会话树分支与导航（P0）

**现状问题**：`runtimeCapabilities.nativeFork = "reserved"`（Pi运行时管理.mjs:166）；fork 实现为复制 JSONL 文件（S5）；恢复为"重开 + 恢复提示词"。**SDK 实际提供 `navigateTree`（同文件树导航 + 分支摘要）与 `fork()`（新文件）**。

**实现步骤**：
1. spike：验证 `SessionManager.create` 打开的会话在多轮工具调用后 `session.navigateTree(earlierEntryId, { summarize: true })` 的行为（含 `SessionTreeNode` 获取入口——经 `session` 或 `SessionManager` 的 projection API）。
2. `Pi运行时管理.mjs`：新增 `navigateSessionTree(sessionPath, targetId, options)` 与 `forkSession(sessionPath, entryId)` 两个生命周期方法；更新 `runtimeCapabilities`：`nativeFork → "available"`。
3. `runs.mjs`：Run 记录新增 `branchOfRunId` 与 `branchPointEntryId` 字段（向后兼容，缺省视为根分支）。
4. `index.mjs`：新增端点 `POST /api/runs/:id/branch`（从指定事件/回合分叉新 Run）；`GET /api/runs/:id` 返回分支链。
5. 前端：Run 详情页新增"从此回合分叉"按钮；`运行轨迹.js` 渲染分支链。
6. fork 后新 Run 的模型上下文 = 树导航到目标节点的投影（`buildSessionProjection`），配 `summarize: true` 生成被弃分支的摘要（SDK 原生 `generateBranchSummary`）。

**预期效果**：
- "恢复/分叉"从"复制文件 + 提示词拼接"升级为原生树导航，上下文保真度显著提升（被弃分支有摘要、不丢工具调用记录）；
- S5 缺口关闭，`runtimeCapabilities` 不再虚报 reserved；
- 为长任务的"试错-回退"工作流（规划类任务高频）提供原生支撑。

**实现成本**：4 人日（spike 0.5 + 后端 2 + 前端 1 + 回归 0.5）。

**风险点**：① `navigateTree` 在 agent 会话（非 TUI）路径的行为细节未验证；② 分支摘要消耗一次模型调用（有成本与延迟）；③ 树节点 id 与项目 Run 事件的映射关系需要设计。
**规避**：spike 先行（P0 闸门）；摘要设为可选（`summarize: false` 时零额外成本）；映射关系只存 `branchPointEntryId` 单向引用，不做双向同步。

### U4 bash 命令硬拦截（P1）

**现状问题**：命令安全策略为应用层字符串匹配，位于工具执行体内；`bash` 工具的 spawn 过程不可拦截，高危命令依赖"事前黑名单 + 事后审计"。

**实现步骤**：
1. 主会话 bash 工具定义改用 `BashSpawnHook`：在 spawn 前回调中执行 `命令安全策略.mjs` 判定，拒绝则抛错（工具返回结构化错误，模型可见）。
2. **Windows powershell 路径同步覆盖**（评审补充）：SDK 有独立的 PowerShell 工具路径（`PowerShellSpawnContext/PowerShellSpawnHook`，core/tools/powershell.d.ts），Windows 主会话可能走 powershell 而非 bash——两个 hook 必须同时接线，否则拦截面出现缺口。
3. `executeBash` 的 `operations` 参数预留注入点：未来可将 `createLocalBashOperations` 替换为受限实现（白名单目录 cwd 锁定、环境变量裁剪），**本阶段不实现沙箱语义，只做钩子接线**。
4. 事件：拦截行为发 `tool_gate_denied`（复用 U2 事件）。

**预期效果**：拦截点从"工具执行体内"前移到"spawn 前"，判定与执行解耦；为后续进程级隔离（U5）预留同一拦截面。

**实现成本**：2 人日。

**风险点**：`BashSpawnHook` 在 SDK 1.1.0 的触发覆盖面（内置 bash 工具 vs 自定义包装）需 spike。
**规避**：spike 验证两种路径；未覆盖路径保留现有执行体内判定。

### U5 进程隔离：bash 侧车执行 + 侧车基建（P1，按评审 R6 降级重述）

**现状问题**：Pi 为进程内库（S2 根因）：模型网络、bash、会话全部与 Node 主进程同域；主进程崩溃即全会话中断；无资源隔离。

**评审修正（R6）**：静态核对 `RpcCommand` 全集（rpc-types.d.ts L14-125）——命令含 prompt/steer/follow_up/abort/bash/compact/fork/switch_session/get_tree 等，**不含 customTools 注册与 setActiveToolsByName**。因此"全量 sidecar（会话整体迁入子进程）"**静态可判 No-Go**（项目核心价值恰在 customTools：officecli/KB/地图/子代理）。U5 主路径据此调整为缩水方案，全量 sidecar 仅在 DSH 适配时以外部内核形态实现。

**实现步骤（缩水主路径）**：
1. 新增 `server/内核侧车.mjs`：通用子进程管理器（spawn/健康检查/崩溃退避 1s/5s/30s/空闲回收/有序关闭）——先服务 bash 侧车执行，**并作为第二阶段 DSH sidecar 的复用基建**（同构生命周期管理）。
2. bash 工具的 `BashOperations` 替换为"侧车执行"实现：`executeBash(command, onChunk, { operations })`（agent-session.d.ts L810 已实证 operations 注入点）把命令派发到子进程执行，stdout/stderr 流式回传；`OAW_PI_SIDECAR=off`（默认）时保持 `createLocalBashOperations` 现状。
3. 崩溃恢复衔接（评审补充）：侧车进程崩溃后，进行中的 bash 命令标记为失败返回（不挂起）；下一次命令触发退避重启；会话本体（JSONL + 上下文）在主进程，无需迁移。
4. **全量 sidecar（原方案）降为 spike 项**：仅当后续 SDK RPC 增加 customTools 注册命令时重评。

**预期效果**：
- bash 执行移出主进程——主进程稳定性与 S2 缺口部分改善（应用级进程隔离，非 OS 级沙箱，诚实标注边界）；
- `内核侧车.mjs` 直接复用于第二阶段 DSH 适配（DSH sidecar 的生命周期管理零重复开发）。

**实现成本**：4 人日（侧车管理 2 + operations 桥 1.5 + 回归 0.5）。

**风险点**：① 流式回传延迟（设性能预算：bash 输出首包延迟增幅 ≤100ms，超出则保持默认）；② Windows 子进程信号处理差异；③ 侧车与主进程的工作区 cwd 一致性。
**规避**：①② 纳入验收脚本；③ 子进程 cwd 显式继承主进程 workspace 且每次命令前校验。

### U6 压缩生命周期事件接入（P1）

**实现步骤**：订阅 `SessionBeforeCompactEvent`（可注入自定义压缩指令：携带当前任务摘要模板）→ 发 `compaction_started` 事件（注册表登记，persist: true）；`SessionCompactEvent` → `compaction_finished`（含前后 token 对比）；`SessionCompactFailedEvent` → `compaction_failed`（当前 SDK 失败是静默的，前端无法感知）。前端运行轨迹渲染压缩节点。

**预期效果**：压缩从"黑盒"变为可观测；失败可见（当前失败后上下文超限的 API 报错会被误判为供应商故障）；`SessionBeforeCompactEvent` 注入任务上下文摘要可提升压缩后任务连续性。

**成本**：2 人日。**风险**：事件载荷结构需 spike；**规避**：载荷字段宽松解析（缺省不渲染）。

### U7 消息投递语义规范（P2）

**实现步骤**：① 用户在 Run 进行中发消息：从"直接 steer"升级为可选 `deliverAs`（前端加"插入引导/排队下轮"二选一，默认保持现状 steer）；② `pendingMessageCount` 与 pending 只读 getter（agent-session.d.ts L626-629）暴露到 Run 状态（前端显示"待投递 N 条"徽标）（评审修正 R9：SDK 无 `getPendingMessages()` 方法，实际为 count 属性 + 两个只读 getter）；③ 预算提醒改用 `followUp` 语义避免打断当前工具执行（当前 steer 会插队）。

**预期效果**：消除"预算提醒打断工具执行"的边界 case；用户排队消息可见。**成本**：1.5 人日。**风险**：低（纯增量 API，默认行为不变）。**规避**：默认值全部保持现状语义。

### U8 事件规范化层（P0，第二阶段前置）

**实现步骤**：
1. 新增 `server/事件规范化.mjs`：定义规范化事件 schema（`{ protocolVersion, eventId, sequence, runId, turnId, toolCallId, type, status, replayable, timestamp, payload }`，复用既有信封字段），提供 `normalizePiEvent(piEvent)` 纯函数。
2. agent.mjs 事件转译层改造为"Pi 事件 → normalizePiEvent → 现有 emit"——**emit 出口与事件注册表/SSE 协议零改动**，仅内部管道规范化（评审修正 R10：该层实际自 L2592 延伸至 ≥3000 行，改造按事件类型分批灰度，不一次性重写）。
3. 订阅管理可选用 SDK `EventBus`（评审标注 R10：该类为 8 行同步 pub/sub，价值有限；可测性收益主要来自第 1 步的纯函数。是否引入以"多订阅者需求真实出现"为准，不作为本项必要组成）。

**预期效果**：事件转换从"内联 switch"变为"可测试纯函数 + 可插拔总线"；**第二阶段 DSH 适配只需实现 `normalizeDshEvent`，前端与 SSE 协议完全不动**。

**成本**：3 人日。**风险**：重构转译层可能引入回归（该层 ≥400 行，是核心链路）；**规避**：先为现有转译层补齐快照测试（`test:sse-protocol` 已有基础），改造后逐事件类型比对输出一致；灰度开关 `OAW_EVENT_NORMALIZE=off` 可一键回退直转路径。

### U9 项目信任治理（P2）

**实现步骤**：用 `ProjectTrustStore` 承接现有工作区信任判定（打开新工作区时的信任确认）：`ProjectTrustDecision` 为三态 `boolean|null`（trust-manager.d.ts L28-33），映射到"首次打开是否需要确认"单一场景（评审修正 R9：不做"信任级别→审批策略"的多级映射，SDK 不支持）；与 `审批策略.mjs` 的联动仅限"未信任工作区默认拒绝写操作"一条规则。**成本**：2 人日。**风险**：与自研权限模型的双轨语义冲突；**规避**：仅在"新工作区首次打开"单一场景接入，不迁移存量判定。

### U10 供应商响应缓存预热（P2）

**实现步骤**：调研 `CacheWarmingDecision/Status` 能力面（SDK 导出类型但文档少），spike 后决定接入范围（仅提示词前缀缓存预热）。**成本**：spike 1 人日 + 接入 2 人日。**风险**：收益依赖供应商前缀缓存支持（DeepSeek/Anthropic 支持，部分不支持）；**规避**：spike 确认无正收益则关闭该项（诚实止损）。

### U11 工具组工厂标准化（P2）

**实现步骤**：子代理工具组装（scout 只读组）从手动逐个 `create*ToolDefinition` 改用 `createReadOnlyTools()`；主会话用 `createCodingTools()` + customTools 合并。**成本**：1 人日。**风险**：低；**规避**：工具名兼容断言测试。

## 5. 本阶段统一风险与验收基线

**统一风险**：
1. SDK 类型存在 ≠ 行为符合预期——**每个优化项实施前必须有对应 spike/单测**（P0 闸门）；U3/U4/U10 spike 失败的显式出口：**关闭该项并记录结论**，不带病合入（评审 R8 补充）；
2. Pi SDK 升级（1.1.x → 后续）可能变更导出面——所有 SDK 调用收敛到 `Pi运行时管理.mjs` 与新模块，agent.mjs 不直接 import 新增 SDK 符号；
3. 回归面大（近 50 个 test:* 脚本）——每个优化项合入前跑 `test:pi-iteration` + `test:sse-protocol` + 对应域测试；
4. feature flag 统一管道（评审 R8）：`OAW_PI_SIDECAR`（U5）/`OAW_EVENT_NORMALIZE`（U8）等开关**统一由新增 `server/运行开关.mjs` 单一模块读取**（env 解析 + 默认值 + 只读快照），经 `/api/status` 下发到前端——禁止各模块直读 `process.env`，避免开关语义分叉。

**统一验收基线**：
- 默认配置下（所有 feature flag off），项目行为与基线**完全一致**（快照测试证明）；
- 每个 U 项开启后有独立验收脚本（scripts/ 下新增，命名 `优化项U{n}验收.mjs`），**且每个验收脚本必须定义可测指标**（评审 R7）：U1 = `getContextUsage()` 精确值 vs 自研估算值的偏差样本记录（验收输出偏差分布）；U2 = hard 模式下"单工具拒绝后 Run 继续完成"的通过率（目标 100%）；U3 = 树分叉后新 Run 上下文与目标节点投影一致性的断言；U6 = 压缩失败事件可见率（100%）；U5 = bash 输出首包延迟增幅 ≤100ms 的实测记录；
- 零新增 npm 依赖（package.json diff 审查）。
