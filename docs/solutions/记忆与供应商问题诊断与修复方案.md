# 记忆系统 / 供应商配置问题诊断与修复方案

> 诊断日期：2026-10-11　基线：v0.11.49　方法：代码静态分析 + 运行态实测复现（非推测）
> 三个问题均为**功能级故障**，非进程崩溃（已核对 `uncaughtException` 处理器与诊断日志，见 1.4）。

## 问题一：记忆与沉淀系统"崩溃"

### 1.1 根本原因：工作区漂移（workspace drift）

记忆系统存在**两套互不一致的工作区来源**：

| 来源 | 取值 | 代码位置 |
|---|---|---|
| 进程全局当前工作区（`getWorkspace()`） | `G:\opencode文件夹` | `.workspace-state.json` → [workspace.mjs:50-60](file:///e:/open plan/server/workspace.mjs#L50-L60) |
| 记忆候选的归属工作区（`proposal.workspace`） | `E:\open plan\office-workspace` | [记忆管理.mjs:146-187](file:///e:/open plan/server/记忆管理.mjs#L146-L187) |

**关键分歧**：记忆**文件面板**永远读全局工作区，记忆**候选列表**按归属工作区过滤。

### 1.2 实测证据（已复现）

```
# 1) 候选归属于 E 盘工作区
GET /api/memory/proposals
  → 1 条，workspace = "E:\open plan\office-workspace"，status=pending

# 2) 但文件面板读的是 G 盘
GET /api/memory
  → {"files":[],"memoryDir":"G:\\opencode文件夹\\memory"}      ← 空

# 3) 批准写入成功了，落到 E 盘
POST /api/memory/proposals/memory_4c1703d9-.../approve
  → {"ok":true,...,"write":{"file":"memory/MEMORY.md"}}
文件系统：E:\open plan\office-workspace\memory\MEMORY.md (144 字节)   ← 确实写了
G:\opencode文件夹\memory 是否存在：False                              ← 面板永远看不到
```

**用户体感 = "沉淀了却什么都没有" = 系统崩溃。** 实际是读写路径分叉。

### 1.3 定位到的故障点（4 处，按严重度）

| # | 故障点 | 位置 | 后果 |
|---|---|---|---|
| F1 | `/api/memory` 路由**完全忽略 workspace 参数**，只认全局 `getWorkspace()` | [index.mjs:4555-4560](file:///e:/open plan/server/index.mjs#L4555-L4560) | 文件面板与候选列表读不同工作区（本次直接病因） |
| F2 | 前端文件列表 `fetch("/api/memory")` **不传 workspace**，而候选列表 `listMemoryProposals(workspace,…)` **传了** | [MemoryTab.jsx:32-42](file:///e:/open plan/client/src/components/MemoryTab.jsx#L32-L42) | 同屏两半数据源不一致 |
| F3 | 候选存储是**单文件全局** `.oaw/memory-proposals.json`，不按工作区分片 | [记忆管理.mjs:12](file:///e:/open plan/server/记忆管理.mjs#L12) | 多工作区候选混池，放大 F1/F2 |
| F4 | 批准/编辑/拒绝/合并 4 个路由**无 try/catch**；`writeMemoryEntry` 会抛 `WriteConflictError`（工作区级锁被活动 Run 持有） | [index.mjs:4630-4657](file:///e:/open plan/server/index.mjs#L4630-L4657) + [写入协调.mjs:186-196](file:///e:/open plan/server/写入协调.mjs#L186-L196) | Agent 运行中批准记忆 → 抛异常 → UI 硬失败 |

补充：`memory_update` 工具内 `createMemoryProposal` 若抛 `MEMORY_CATEGORY_INVALID` / `MEMORY_WORKSPACE_INVALID`（[记忆管理.mjs:42-44,51-58](file:///e:/open plan/server/记忆管理.mjs#L42-L58)），异常会直接冒泡进 Agent 回合（[agent.mjs:2252](file:///e:/open plan/server/agent.mjs#L2252)）。

### 1.4 已排除：不是进程崩溃

- [index.mjs:5285-5293](file:///e:/open plan/server/index.mjs#L5285-L5293) 注册了 `uncaughtException` → 记 `processFault` 后退出
- `%APPDATA%\规聚\诊断.log` **不存在** → 从未发生未捕获异常
- `服务监督.log` 无异常重启记录
- **结论**：无崩溃日志，属"静默失效"，用户感知即崩溃

### 1.5 复现路径（三步，稳定复现）

1. 把工作区切到任意**不含 memory/** 的目录（如 `G:\opencode文件夹`），确认 `.workspace-state.json` 已写入该路径
2. 用另一个工作区（如 `office-workspace`）的会话让 Agent 调 `memory_update` 生成候选
3. 打开记忆治理面板点"批准" → 返回成功，但文件面板始终为空

### 1.6 修复方案

**修复 F1（必做，5 行）** — `/api/memory` 接受 workspace，并复用与候选一致的解析：

```js
// index.mjs:4555 附近
app.get("/api/memory", (req, res) => {
  try {
    const ws = req.query.workspace ? normalizeWorkspace(req.query.workspace) : getWorkspace();
    \.\.\.
    const dir = path.join(ws, "memory");   // 不再用无参 getMemoryDir()
    res.json({ files: listMemoryFiles(dir), memoryDir: dir, workspace: ws });
  } catch (e) { res.status(500).json({ error: e.message }); }
});
```
并把 `listMemoryFiles/getAgentsMd` 改为**接受 dir 参数**（去掉对全局 `getWorkspace()` 的隐式依赖）。

**修复 F2（必做，3 行）** — 前端两处调用统一带上 workspace：

```js
// MemoryTab.jsx:35
fetch(`/api/memory?workspace=${encodeURIComponent(workspace)}`)
```

**修复 F3（建议）** — 候选按工作区分片，消除混池：

```js
// 记忆管理.mjs:61-64
function proposalsFile(workspace) {
  // 全局旧文件保留为只读迁移源
  return path.join(requireWorkspace(workspace), ".oaw", "memory-proposals.json");
}
```
`createMemoryProposal` 已持有 `workspace`，`listMemoryProposals` 亦已按 workspace 过滤，改动面小；旧文件首次读取时按 `proposal.workspace` 分组迁移。

**修复 F4（必做，防御）** — 4 个路由包 try/catch，把异常转结构化响应：

```js
app.post("/api/memory/proposals/:id/approve", (req, res) => {
  try {
    sendMemoryResult(res, agentManager.approveMemoryProposal(req.params.id, { /* … */ }));
  } catch (e) {
    res.status(e.code === "WRITE_CONFLICT" ? 409 : 500)
       .json({ ok: false, code: e.code || "MEMORY_APPROVE_FAILED", error: e.message, details: e.details || null });
  }
});
```
同时把 `writeMemoryEntry` 的锁获取换成已有的 `acquireWriteLockWithRetry`（[写入协调.mjs:252](file:///e:/open plan/server/写入协调.mjs#L252)，20s 退避重试），把"运行中批准必失败"变成"稍等即可成功"。

**修复工具侧异常（必做）** — [agent.mjs:2252](file:///e:/open plan/server/agent.mjs#L2252) 包 try/catch，失败返回工具级文本而非抛出：

```js
let proposal;
try {
  proposal = createMemoryProposal({ /* … */ });
} catch (e) {
  return { content: [{ type: "text", text: `记忆建议未能保存：${e.message}` }], details: { error: e.code || "MEMORY_CREATE_FAILED" } };
}
```

### 1.7 验收标准

- 面板显示的文件数 == 实际 `memory/` 目录文件数（任意两个工作区间切换均成立）
- Agent 运行中批准候选 → 成功或返回 409 且带明确文案，**不出现 500 / 白屏**
- `memory_update` 传入非法分类 → 返回工具级提示，**Agent 回合不中断**
- 回归：`npm run verify` + 新增 `tests/记忆工作区一致性.test.mjs`（断言 F1/F2 修复）

## 问题二：凭证配置页缺失 "opencode go" 套餐

### 2.1 根本原因：三层叠加

**第一层（致命）：套餐生成的 provider id 与 pi 原生 id 不匹配。**

pi 原生就支持 OpenCode Zen/Go，其 provider id 是 **`opencode`**，凭据环境变量 `OPENCODE_API_KEY`：

```
node_modules/@earendil-works/pi-coding-agent/docs/models.md
| `opencode` | `jev-1.13`, `jev-1.13-free` | `OPENCODE_API_KEY` |
```

但 [套餐目录.mjs](file:///e:/open plan/server/套餐目录.mjs) 生成的是合成 id：

```js
function planProviderId(planId) {
  return `PLAN_${String(planId).toUpperCase()...}`;   // → PLAN_OPENCODE_ZEN_GO
}
```

→ 写进 `模型配置.json` / `凭据.json` 的是 `PLAN_OPENCODE_ZEN_GO`，而 pi 的运行时按 `opencode` 解析内置目录与 `OPENCODE_API_KEY`，**对不上**；`PROVIDER_LABELS` 里预置的又是不存在的第三套 `"opencode-go"`（[SettingsPanel.jsx:59](file:///e:/open plan/client/src/components/SettingsPanel.jsx#L59)）。**三套命名，互不相认。**

**第二层：凭证页的供应商下拉是"静态 + 派生"列表，从不合并套餐目录。**

```js
// SettingsPanel.jsx:691-696
const providerOptions = [...new Set([
  ...availableModels.map((i) => i.provider).filter(Boolean),
  ...modelConfigs.map((i) => i.provider).filter(Boolean),
  ...Object.keys(providers || {}),
  "anthropic", "openai", "gemini", "deepseek", "moonshot", "qwen", "custom",   // ← 硬编码
])];
```
套餐未接入时不在任何来源中；即使接入，id 也是 `PLAN_*`，仍不改写这个列表。

**第三层：两个子系统独立。** "模型套餐" Tab 与"凭证页"各自维护供应商概念，无共享注册表。

### 2.2 排除项（避免误判）

| 怀疑 | 结论 | 依据 |
|---|---|---|
| 配置遗漏 | 部分成立 | `PROVIDER_LABELS` 有 `opencode-go` 却无人生成该 id |
| 权限限制 | **否** | `/api/agent/plans` 实测 200，返回套餐；`/api/agent/plans/models` 返回 45 个模型 |
| 版本适配 | **否** | pi 1.1.0 的 models.md 明确含 `opencode` |
| 数据未同步 | **否** | 套餐目录为内存注册表，非缓存 |

### 2.3 验证步骤

```powershell
# 1) 套餐接口正常
Invoke-RestMethod http://127.0.0.1:3002/api/agent/plans
#    → plans[0].providerId = "PLAN_OPENCODE_ZEN_GO"   ← 问题所在

# 2) 凭证接口中没有 opencode
Invoke-RestMethod http://127.0.0.1:3002/api/agent/auth
#    → providers 仅 MINMAX

# 3) 对照 pi 原生 id
Select-String node_modules/@earendil-works/pi-coding-agent/docs/models.md -Pattern "opencode"
#    → | `opencode` | ... | OPENCODE_API_KEY |
```

### 2.4 修复方案

**修复一（根因，必做）** — 套餐改用 pi 原生 provider id，不再合成：

```js
// 套餐目录.mjs
export const PLAN_PRESETS = [{
  planId: "opencode-zen-go",
  providerId: "opencode",           // ← pi 原生 id（新增显式字段）
  name: "OpenCode Zen Go",
  api: "openai-completions",
  baseUrl: "https://opencode.ai/zen/go/v1",
  envVar: "OPENCODE_API_KEY",
  keyUrl: "https://opencode.ai/zen",
  modelsSource: "remote",
}];
// 删除 planProviderId()，全部改用 preset.providerId
```
这样 `auth.json` 的 key 与 `models.json` 的 provider 都与 pi 内置目录对齐，且 pi 自身能从环境变量兜底解析。

**修复二（必做）** — 凭证页下拉合并套餐与预设目录：

```js
// SettingsPanel.jsx:691
const providerOptions = [...new Set([
  ...availableModels.map((i) => i.provider).filter(Boolean),
  ...modelConfigs.map((i) => i.provider).filter(Boolean),
  ...Object.keys(providers || {}),
  ...plans.map((p) => p.providerId),        // ← 新增：套餐目录
  ...PROVIDER_PRESETS.map((p) => p.id),     // ← 新增：内置预设（见问题三）
])];
```

**修复三（必做）** — 清理命名三套并存：以 pi 原生 id 为唯一键，`PROVIDER_LABELS` 增加 `opencode: "OpenCode Zen Go"`，删除误导性的 `"opencode-go"`。

## 问题三：内置供应商覆盖对齐原生 pi

### 3.1 现状差距（实测）

| 指标 | 规聚当前 | 原生 pi |
|---|---|---|
| 可用供应商 | **1**（MINMAX） | **≈40** |
| 模型数 | 4 | 数百 |
| 来源 | `localModelProviders()` 过滤后 | ModelRuntime 内置目录 + models.dev |

**唯一闸门**在 [agent.mjs:624-634](file:///e:/open plan/server/agent.mjs#L624-L634)：

```js
function localModelProviders() {
  const providers = new Set([
    ...Object.keys(readModelsStore()),     // 模型目录缓存.json = {}（空）
    ...Object.keys(readModelsConfig()?.providers || {}),  // 仅 MINMAX
    ...Object.keys(readCredentials()),     // 仅 MINMAX
  ]);
  return new Set([...providers].filter(...));
}
```
而 [agent.mjs:3896](file:///e:/open plan/server/agent.mjs#L3896) `listModelCatalog()` 把它当作白名单：
```js
const runtimeModels = [...mr.getModels()].filter((m) => providers.has(m.provider) && ...);
```
→ **凡是未在本地配置里出现过的供应商，一律不可见**，哪怕 pi 原生完全支持。

### 3.2 技术路径（推荐：以 pi 运行时为唯一真源）

**核心原则：不要手抄 40 个供应商，而是从 pi 的 ModelRuntime 枚举。** 这样 SDK 升级时自动同步，避免二次维护漂移。

**步骤 1 — 新增供应商目录接口**（`server/供应商目录.mjs` 新建）

```js
export async function listProviders(mr) {
  const all = [...mr.getModels()];                    // ← 不套 localModelProviders 过滤
  const byProvider = new Map();
  for (const m of all) {
    const id = m.provider;
    if (!byProvider.has(id)) byProvider.set(id, { id, name: m.providerName || id, models: 0, sample: [] });
    const p = byProvider.get(id);
    p.models += 1;
    if (p.sample.length < 3) p.sample.push(m.id);
  }
  const configured = new Set(Object.keys(readCredentials()));   // 已配凭据
  return [...byProvider.values()]
    .map((p) => ({ ...p, configured: configured.has(p.id), apiKeyEnv: PRESET_ENV[p.id] || null }))
    .sort((a, b) => Number(b.configured) - Number(a.configured) || b.models - a.models);
}
```

**步骤 2 — 路由**（`index.mjs`）
```js
app.get("/api/agent/providers", async (_req, res) => {
  try { res.json({ providers: await agentManager.listProviders() }); }
  catch (e) { res.status(500).json({ error: e.message, code: "PROVIDERS_FAILED" }); }
});
```

**步骤 3 — 内置预设表**（可选增强，提供中文名/环境变量/套餐入口）

按 pi `docs/providers.md` 的 API-key 表建立 `PRESET_ENV` 映射（**不含 baseUrl**——pi 内置目录已带，只有自定义端点才需用户填）：

### 3.3 适配工作量

| 工作项 | 规模 | 说明 |
|---|---|---|
| `供应商目录.mjs` + 路由 | 小 | 约 80 行，无外部依赖 |
| `PRESET_ENV` 表 | 小 | 约 40 行常量，来源 pi docs，可脚本生成 |
| 凭证页下拉两段式 | 中 | SettingsPanel.jsx 局部改造 |
| `PROVIDER_LABELS` 补全 | 小 | 常量表 |
| 单测 | 小 | 断言"未配置 provider 也在列表中"、id 与 pi 一致 |
| 依赖 | **无** | 复用既有 ModelRuntime 与凭据写入 |

**风险点**：`mr.getModels()` 是否真的返回全部内置供应商需实测一次（当前被 `localModelProviders` 遮蔽，未验证）。若 SDK 只返回已配置项，则退化为"内置预设表 + 按需 `models.json` 注册"方案——工作量增加有限。

### 3.4 兼容性保障

1. **不破坏现有配置**：`MINMAX` 等既有 provider 行为不变；新目录仅**只读枚举**，写入仍走 `setApiKey`
2. **id 唯一真源为 pi 原生 id**：与问题二修复一致，杜绝 `PLAN_*` / `opencode-go` 类合成 id
3. **env 兜底不覆盖显式凭据**：pi 规范为「auth.json 优先于环境变量」，保持现状
4. **离线可用**：目录来自运行时缓存，网络不可达时降级本地缓存（现有 `mr.refresh` 已容错）
5. **回归门禁**：`npm run verify` + 新增 `tests/供应商目录.test.mjs`

### 3.5 验收标准

- `GET /api/agent/providers` 返回 ≥ pi docs 所列的 API-key 类供应商数量
- 凭证页下拉可选到 `opencode`（OpenCode Zen Go）等，选中后提示环境变量名
- 保存 `opencode` 凭据后，`/api/models` 出现 opencode 系列模型且 `available=true`
- 既有 MINMAX 会话不受影响

## 附：三项问题的共同根因

问题二、三共享同一深层缺陷：**规聚自建了一套与 pi 原生不一致的 provider 标识体系**（`PLAN_*` 合成 id + 硬编码 7 项下拉 + `localModelProviders` 白名单）。
问题一则是**工作区标识在记忆子系统内不统一**。
两者的修复方向一致：**收敛到单一真源**——provider 用 pi 原生 id，工作区用显式传入的 workspace 参数，而非进程全局单例。
