# 第二阶段：DSH 内核最小侵入适配方案与改动清单

- 日期：2026-10-15
- 前置文档：[第一阶段：基于 PI SDK 原生能力的优化方案](./2026-10-15-PI-SDK原生能力优化方案.md)
- 对标内核：DeepSeek Harness（`dsh --profile sdk`，JSON-RPC over stdio sidecar）
- **硬约束**：最小改动；不对核心业务逻辑与原有功能链路做大规模重构；不影响现有功能正常运行；每一处改动有明确兼容保障与回滚方式

---

## 0. 结论摘要

1. **适配采用"增量分派"而非"重构收敛"**：不动 `agent.mjs` 约 100 处 Pi 耦合，不改事件注册表/协议/存储，不改 `Pi运行时管理.mjs`。DSH 适配的全部改动 = **3 个新增文件 + 5 处受控增量分支（合计约 80 行）+ 1 个验收脚本**。
2. **V1 范围收窄**：DSH 内核仅覆盖 **Chat 基本链路**（prompt → 流式 token → 内置工具 → run_finished），业务工具（Office/KB/地图）不桥接（列 V2）。理由：最小改动优先级高于能力覆盖；业务工具桥接需要新增 MCP server 模式（现 `mcp管理.mjs` 仅为 client），改动面与风险显著更大。
3. **两个硬前置来自第一阶段**：U8 事件规范化（`normalizePiEvent` 纯函数 + EventBus）使 DSH 适配只需实现 `normalizeDshEvent`；U5 侧车基础设施（`PiSidecar.mjs`）泛化为 `内核侧车.mjs` 后由 DSH 复用（启动/健康检查/退避重启/有序关闭/事件桥完全同构）。
4. **单一总开关**：`OAW_DSH_KERNEL`（默认 `off`）。关闭时项目行为与基线**完全一致**（快照测试证明）；开启且 `kernelId=dsh` 时才进入 DSH 路径。

## 1. 架构（适配后）

```
POST /api/agent/prompt { kernelId? }          ← C4：新入口参数 + 分派闸门
        │
        ▼
【分派闸门（C6，位于 index.mjs POST handler 内、beginRun 之前）】
   评审修正 R1：现有链路 admission → beginRun(runs.mjs:551) → planTaskCapabilities
   → officecli 预检 → capability_plan 事件 → executeAgentRun（index.mjs:3875，被 4192 调用）
   全部发生在 executeAgentRun 函数体之前/之内，因此分派必须在 POST handler 的
   beginRun 之前完成，而非 executeAgentRun 内部。
        │
   ├─ kernelId="pi"（默认/缺省）→ 原有全部预处理与执行路径（零改动）
   └─ kernelId="dsh"（需 flag on；携带 task/workflow 时 400，见 R3）
        → 跳过 planTaskCapabilities 与 officecli 预检（R2：生成 DSH 简化契约）
        → server/DshKernelAdapter.mjs（C2，新增）：dshExecuteRun
            （复用 recordRunEvent/finishRun 写 Run 记录，不重复 beginRun）
                │
                ▼
      server/内核侧车.mjs（C1，U5 泛化）
                │ 子进程：dsh --profile sdk（JSON-RPC over stdio）
                ▼
      DSH Runtime（$DSH_HOME 独立配置域；approval 强制确认模式，见 R4）
                │
    normalizeDshEvent() → 现有事件注册表类型（不新增类型）
                ▼
    现有 emit 出口 / Run 记录 / SSE（全部零改动）
```

**关键设计**：DSH 事件不新增事件类型，全部映射到现有注册表类型（`run_started`/`token`/`tool_start`/`tool_output`/`tool_end`/`run_finished`/`agent_error`）。事件层（注册表/协议/存储/前端投影）因此**零改动**。

## 3. 明确不做的事（排除项，即"最小改动"边界）

| 排除项 | 理由 | 影响 |
|---|---|---|
| 收敛 `agent.mjs` ~100 处 Pi 耦合 | 属大规模重构，违反硬约束 | DSH 适配不经过统一 KernelAdapter 抽象（第一阶段 U 系列也不做），采用增量分派；后续若做双内核深度化再评估 |
| 事件注册表/协议/存储改动 | 事件层是全前端契约，改动即大范围回归 | DSH 事件全部映射到现有类型；DSH 特有事件（如 Trajectory 细节）V1 不透传 |
| `Pi运行时管理.mjs` 改动 | Pi 主路径保持原样 | Pi 内核行为零变化 |
| 会话数据互转/迁移 | 可行性报告 §6.3 已定论：按内核并存，不做双向迁移 | DSH 会话存 `$DSH_HOME`；跨内核续话用"新建会话 + 上下文摘要"（现状恢复策略） |
| 业务工具（Office/KB/地图/记忆）桥接 | 需新增 MCP server 模式（`mcp管理.mjs` 仅为 client），改动面大 | **V1 的 DSH 内核仅有 DSH 内置工具**（bash/read/write 等，受 DSH 自身沙箱与审批约束）；业务工具桥接列 V2 |
| 前端差异化面板（Trajectory 视图等） | UI 面大 | V1 仅内核徽标与选择器；运行详情复用现有投影 |
| DSH 插件/profile patch 定制 | 引入 Cordis 学习成本 | 使用 `sdk` profile 原样启动 |

## 4. 适配验证方案

### 4.1 Spike 闸门（适配开发前，Go/No-Go）

| # | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| S1 | `dsh --profile sdk` 子进程可驱动 | spike 脚本 spawn + JSON-RPC 握手 | 3s 内 handshake 成功 |
| S2 | 事件订阅协议 | 发 prompt 订阅事件流 | 收到完整 token 流 + 终态事件 |
| S3 | 模型凭据复用 | `ctx.llm` 指向现有供应商 baseUrl/key | 模型响应正常 |
| S4 | Windows 稳定性 | 冷启动耗时 / 稳态内存 | 冷启动 <5s；稳态 <400MB |
| S5 | abort/取消语义 | 中断进行中 prompt | 事件流有序终止 |

**任一项不通过**：本方案降级为"仅完成 C1/C3/C8 的注册表与 UI 骨架（无 DSH 实际接入）"，等待 DSH 版本成熟后重评。

### 4.2 验收脚本（C9，`scripts/DSH适配验收.mjs`）

- **A1 行为零变化**（最关键）：`OAW_DSH_KERNEL=off` 启动 → 跑 `test:pi-iteration` 全套 + `test:sse-protocol` + 设置面板 DOM 快照 → 全部通过且与基线一致；
- **A2 开关拒绝语义**：flag off 时 `kernelId="dsh"` 请求返回 400 且错误文案明确；**flag on 但携带 task/workflow 时同样 400**（评审 R3 断言）；
- **A3 Chat 链路**：flag on + kernelId=dsh 发送真实 prompt → 断言事件序列（run_started/token ≥1/tool_end 可选/run_finished）齐全且**形状与 Pi 路径一致**（同一断言函数复用）；**断言 capability_plan 为 DSH 简化契约（provider="dsh"、routing.officecli="none"，评审 R2）**；**断言 DSH 写操作触发 tool_approval_request 且自动批准关闭时 Run 等待审批（评审 R4）**；
- **A4 双内核并行**：同时发起 Pi 与 DSH 会话 → 互不干扰、Run 记录各自正确；
- **A5 崩溃隔离**：kill DSH 子进程 → Pi 会话不受影响；DSH 侧车按退避策略重启；
- **A6 Run 记录兼容**：新旧 Run（含/不含 kernelId 字段）在 `GET /api/runs/:id` 与前端详情页均正常渲染。

## 5. 风险评估（适配专项）

| 等级 | 风险 | 缓解 |
|---|---|---|
| 高 | DSH RC 版本破坏性变更（官方明示） | 版本锁定（package.json 固定 dsh 版本）；适配器隔离（C2 单文件承载全部 DSH 语义）；Spike 每次升级重跑 |
| 高 | JSON-RPC 协议细节与预期不符 | §4.1 五项 Spike 为硬闸门，不通过即降级 |
| 中 | DSH 82 依赖的供应链与体积 | sidecar 按需启动 + 空闲回收；不进入主进程依赖树（子进程独立 node_modules） |
| 中 | 双内核并发资源争抢 | 侧车独立进程；Pi 路径零感知；资源预算（稳态 <400MB）纳入 A4 断言 |
| 低 | 前端 flag 状态获取失败 | `/api/status` 已有；flag 获取失败时按 off 处理（fail-safe 默认） |
| 低 | 用户误开 DSH 后预期落差（无业务工具） | 设置面板 DSH 选项标注"实验：仅对话链路"；400 错误文案同口径 |

## 6. 兼容性承诺汇总

1. **默认配置行为零变化**：`OAW_DSH_KERNEL` 缺省 off，全部现有请求体/UI/事件逐字节等价（A1 快照证明）。
2. **Pi 路径代码零改动**：C6 分派位于所有现有逻辑之前；`Pi运行时管理.mjs` 不在改动清单中。
3. **事件契约零扩展**：DSH 事件映射到现有注册表类型，前端投影/SSE 协议/事件存储不动。
4. **数据零迁移**：Run 记录仅追加可选字段；DSH 会话独立存储域。
5. **单提交可回滚**：全部改动（含新文件）为独立提交，`git revert` 一次还原。
